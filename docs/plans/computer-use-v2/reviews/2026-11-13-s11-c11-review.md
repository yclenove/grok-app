# S11-0c C11 independent code review — 2026-11-13

**Verdict: changes requested. Two P1 findings and four P2 findings; no P0 found.** The present results must not be used as a bound for ADR 0019's M4a schedule: the reported RTT omits publication time, and an over-five-second round can pass.

Reviewed branch `cu2/s11-c11`, commits `78f966be` and `1ec5d796`, against base `fcb619f7` and `/tmp/cu2-orch/grok-c11.md`. All source references below are relative to `computer-use/`. The review covers C11 and its reuse of stage M; it does not reopen the previously reviewed ownership, SSH, or volume machinery.

## Findings

### 1. P1 — RTT starts after an operation during which the entire exchange can complete

**Evidence:** `tools/s11-mailbox-probe/src/c11.rs:352`, `tools/s11-mailbox-probe/src/c11.rs:356`, `tools/s11-mailbox-probe/src/c11.rs:360`; `tools/s11-mailbox-probe/src/io.rs:590`, `tools/s11-mailbox-probe/src/io.rs:600`. The changed definition is also documented at `tools/s11-mailbox-probe/src/c11.rs:12` and `docs/s11-0-probe-runbook.md:108`.

`pwrite64` performs the write and synchronous `fsync` before the host records `t0`. A guest can observe that write and publish its pong while the host is still in `fsync`. The next host read then finds an existing pong and reports only the residual time after `fsync`, excluding the write, visibility, and reaction that already happened. This is not the requested write → guest visibility/reaction → host visibility/read interval, and is not an upper bound on it. The documentation consistently describes the shorter interval, but that does not satisfy the brief or the scheduling use of this measurement.

**Reproduction:** with the unmodified binary and a real local guest-role process, an `LD_PRELOAD` shim delayed each host `ip-hg` `fsync` return by 200 ms. Both processes completed eight rounds with exit 0. Wall time was 1,641 ms, but the host reported `rtt_us=n=8,min=40,p50=50,max=112 verdict=ok`. The guest completed its reactions during those excluded waits.

**Minimal fix:** encode the record first, then start the host clock immediately before `pwrite64`, retaining the existing write-then-fsync ordering and ending after a validated pong read. If the post-fsync residual is useful, report it as a separate diagnostic. Update the README/runbook definition and add a controlled slow-fsync case that cannot report a near-zero full RTT.

### 2. P1 — A successful read can cross the five-second round deadline and still produce `ok`

**Evidence:** `tools/s11-mailbox-probe/src/c11.rs:195`, `tools/s11-mailbox-probe/src/c11.rs:198`, `tools/s11-mailbox-probe/src/c11.rs:203`, `tools/s11-mailbox-probe/src/c11.rs:357`, `tools/s11-mailbox-probe/src/c11.rs:395`, `tools/s11-mailbox-probe/src/c11.rs:406`; terminal checking at `tools/s11-mailbox-probe/src/run.rs:499` checks the command deadline, not the round deadline.

`wait_got` checks deadlines before calling the reader, then immediately accepts a matching sequence when that call returns. Neither `pread` nor reopen/open/fstat/pread has a round postcheck. If a read starts before five seconds and returns a valid pong after five seconds, the round succeeds. On the last round there is no next iteration to detect that overrun. The guest similarly has no round postcheck after its pong write/fsync. The outer 50/60-second command bounds do not enforce the promised five seconds per round.

**Reproductions:** an in-memory test using the existing clock hook advanced the clock from the round start to +6 seconds inside the read closure and returned `encode(1)`; `wait_got` returned `Ok(Seen)` instead of timeout. Separately, delaying the real host's final valid `pread64` return by 5.1 seconds produced exit 0 on both roles and `rtt_us=n=8,min=22,p50=5101,max=5100167 verdict=ok reason=-`.

**Minimal fix:** recheck both original deadlines immediately after each read and before accepting a hit, and after a guest pong write/fsync before counting the round or emitting success. Keep the original round end; do not renew it. Add a valid-read-crosses-deadline test, including the last round. The existing timeout test at `tools/s11-mailbox-probe/src/c11.rs:586` advances time only during a miss/retry and therefore misses this path.

### 3. P2 — The first RTT includes SSH/process startup because C11 omits the readiness barrier

**Evidence:** `scripts/s11-0-probe.sh:1307`, `scripts/s11-0-probe.sh:1310`; `tools/s11-mailbox-probe/src/c11.rs:342`, `tools/s11-mailbox-probe/src/c11.rs:347`, `tools/s11-mailbox-probe/src/c11.rs:352`. C1 waits for readiness before measuring at `tools/s11-mailbox-probe/src/run.rs:967`.

Starting background SSH is not proof that the guest probe has opened its files and entered its poll loop. C11 immediately publishes sequence 1 and starts timing. Consequently, its eight-sample maximum includes connection/authentication, remote digest checking, and probe startup when those finish after the host write. This can dominate the faster in-place mechanism the case is intended to measure, independently of the five-millisecond polling interval. It also spends the first round's timeout on startup.

**Reproduction:** delaying only guest-process launch by 350 ms gave `rtt_us=n=8,min=33,p50=5123,max=351285 verdict=ok`, with 69 all-zero-placeholder reads counted as torn. No filesystem visibility delay was introduced.

**Minimal fix:** add an explicit bounded guest-ready exchange before starting sequence 1 or its round clock. A canonical sequence-0 readiness record in the already pre-created `ip-gh` can avoid introducing another pathname or rename. Test that delaying guest readiness leaves startup outside all eight RTT samples.

### 4. P2 — C11 never collects or validates the guest summary

**Evidence:** `tools/s11-mailbox-probe/src/c11.rs:283`, `tools/s11-mailbox-probe/src/c11.rs:389`, `tools/s11-mailbox-probe/src/c11.rs:400`; `scripts/s11-0-probe.sh:1312`, `scripts/s11-0-probe.sh:1313`, `scripts/s11-0-probe.sh:1280`, `scripts/s11-0-probe.sh:1221`. The C11 SSH stub at `scripts/test_s11_0_probe.sh:197` exits 0 without producing a guest record, and `scripts/test_s11_0_probe.sh:1958` still expects the case to pass.

The Rust guest emits its own torn count, per-round polls, and guest-clock gaps, but the host ignores both its captured SSH output and `result-guest`. Settlement requires only a zero SSH exit and a host record. Missing or malformed guest summaries therefore do not prevent `ok`; guest observations are absent from the JSON case record. A guest-side rollback/skip is also reduced to a generic nonzero-exit/host-timeout result rather than preserving the guest failure. The requested strict guest-record parsing is entirely absent, rather than merely permissive.

**Minimal fix:** parse one bounded guest summary from the captured SSH output with a C11-specific exact schema: fixed version/op/guest role, matching mode, bounded numeric fields, consistent completed-round/poll/gap counts, and compatible verdict/reason. Retain the validated guest diagnostics alongside the host record; guest values must not replace locally measured host RTT/count fields. Missing/malformed evidence must make the case unknown, and an explicit guest rollback/skip must remain failed. Add negative guest-summary stubs; the current successful stub must emit a valid guest summary.

### 5. P2 — The C11 parser permits a timeout record to take the successful `not-ack` path

**Evidence:** `scripts/s11-0-probe.sh:1197`, `scripts/s11-0-probe.sh:1220`, `scripts/s11-0-probe.sh:1226`, `scripts/s11-0-probe.sh:1273`, `scripts/s11-0-probe.sh:1280`, `scripts/s11-0-probe.sh:1514`, `scripts/s11-0-probe.sh:1551`.

The global parser allows `not-ack`, but the new C11 branch only constrains the reasons for `ok` and `failed`. C11's settlement then accepts `not-ack` with eight rounds and a matching mode. Two such sub-cases aggregate to `not-ack`, which is treated as successful collection. That verdict belongs to C2's publication-boundary experiment and is not a C11 result.

**Reproduction:** the production `parse_fields` and `settle_host c11` functions accepted this exact line with all process statuses clear:

```text
v=1 op=c11 role=host mode=fd n=8 torn=0 rtt_us=n=8,min=10,p50=20,max=30 verdict=not-ack reason=timeout
```

They returned `SHAPE_OK=1`, `M_VERDICT=not-ack`, `M_REASON=timeout`, and status 0. The Rust producer does not normally generate this combination; it is an input-validation defect in the newly added branch.

**Minimal fix:** restrict C11 to `ok|unknown|failed` in its parser and allow only `ok` through its success settlement. Add a negative parser/stub case for the line above, so a timeout-bearing or unsupported verdict cannot receive the successful aggregate exit path.

### 6. P2 — New C11 preparation commands execute outside the bounded runner

**Evidence:** `scripts/s11-0-probe.sh:1002`, `scripts/s11-0-probe.sh:1009`, `scripts/s11-0-probe.sh:1010`, `scripts/s11-0-probe.sh:1061`, `scripts/s11-0-probe.sh:1506`.

`seed_c11_files` invokes `mktemp`, `mv`, `cp`, and error-path `rm` directly from the orchestration process. In particular, `mv` moves from `WORKDIR` to the export: these can be different filesystems when temporary storage is local and `--out` is on the Mini's external volume. A stalled copy/move is not supervised by `run_bounded`, so the attempt deadline cannot stop preparation or advance to cleanup/quarantine. These are new C11 external calls, not the previously reviewed VM/SSH lifecycle.

The final destinations also do not have explicit exclusive/no-follow creation: `mv` can replace `ip-hg`, and `cp` can follow an existing `ip-gh` symlink. The fresh 0700 directory and pre-VM ordering prevent a guest from planting those destinations in the intended path, so this review found no demonstrated host-path escape. They nevertheless do not provide the explicit creation semantics requested for C11.

**Minimal fix:** create both 64-byte files directly in the private export through an exclusively creating, no-follow helper supervised by the existing bounded runner, before VM start. Avoid the cross-filesystem move/copy. Preserve unknown/quarantine handling if the helper cannot be proved finished. Add a stalled-preparation stub and assert file existence/size at the stubbed `tart run`, rather than only after the attempt.

## Verification and coverage limits

- Separate `bash -n` checks passed for both scripts; `git diff --check fcb619f7..HEAD` passed.
- The suite's static checks and its existing `dispatcher-c11` and `stage-m-c11` cases passed on Linux/gawk/Bash 5.2. The functions were loaded into an in-memory harness with temporary artifacts under `/tmp`; repository scripts were unchanged.
- `cargo test --offline --locked` passed: 53 unit tests, including all nine C11 tests, and two integration tests. Cargo/build artifacts were redirected to `/tmp`. The C11 codec, retry, rollback/skip, and two-thread exchanges exercise real logic and IO. They do not test delayed successful reads, fsync overlap, startup exclusion, descriptor retention across pathname replacement, or strict guest-summary settlement.
- The existing shell C11 test checks two launches/modes, report labels, and retained zero-filled 64-byte files. It checks preparation after the attempt, not at VM start, and supplies neither a guest summary nor negative C11 settlement cases. Dispatcher acceptance reaches the allowed arm but stops at its missing-probe check; final guest argv are checked textually.
- The additional clock-hook and local interposition experiments reproduced findings 1–3; direct production-function evaluation reproduced finding 5. These are local fault injections, not virtiofs measurements.
- The complete shell suite, release-profile Rust tests, actual bash 3.2, and macOS/virtiofs behavior were not executed for this review. No real Tart, SSH, or disk-image operations were performed. No product code was edited and no commit was made; this report is the only repository change.
