1. **P1 / must-fix — Timeout recovery still contains an unbounded wait.** `tests/tart_offline/watch.rs:83`, `tests/tart_offline/watch.rs:84`; error exits at `tests/tart_offline/watch.rs:63` and `tests/tart_offline/watch.rs:81`. Impact: offline test liveness; no production execution bypass.

   **Failure scenario:** The parent reaches its deadline with a live child, discards an error from `child.kill()`, then calls blocking `child.wait()` without a deadline. If termination fails while the child remains live, the supposedly independent watchdog now waits indefinitely on that child. Even after a successful kill request, the code does not bound observation/reaping of the exit. A `try_wait` error instead panics and drops `Child`, whose Drop does not kill/reap it. These paths do not establish the promised bounded failure and cleanup. Ordinary successful kill followed by wait does reap correctly; an actual OS failure was not observed in this static review.

   **Minimal fix:** Check the kill result, retain a monotonic cleanup deadline, and observe exit with bounded `try_wait` polling rather than an unconditional blocking wait. Allow cleanup time inside the stated ceiling. On polling/termination/reap errors, attempt cleanup within that budget and return a nonzero, explicitly unclean result; do not claim successful kill/reap without observing exit. No userspace code can guarantee cleanup when the OS refuses termination, but the parent can still avoid waiting forever or falsely reporting cleanup. Cover a failed/no-op termination and delayed exit with a bounded harness test. This needs no observer thread, production process supervisor, or VM lifecycle machinery.

   **Mutation coverage:** Removing the kill at line 83 makes the existing deliberately hanging-child check hang in `wait`, rather than fail within its own limit. Returning a fabricated `Supervised { killed: true, code: 128 }` without touching the child would also satisfy the present self-check at `tests/tart_offline.rs:50`; the check does not independently establish absence. These are static predictions, not mutations executed here. The injected-hang check is useful evidence for the normal kill path, not protection for all wrapper regressions.

2. **P2 / should-fix — The clone tests protect the shorter permit deadline, but not the shorter call deadline.** `tests/tart_offline/review_fixes.rs:68`, `tests/tart_offline.rs:758`; implementation at `src/disposable/tart/runner.rs:130`. Impact: regression coverage of a required deadline invariant; current implementation is correct.

   **Failure scenario / surviving mutation:** Replace `deadline.at().min(permit.absolute_deadline())` with `permit.absolute_deadline()`. Both new clone tests still pass because their permit deadline is earlier than the call deadline. The older command-inventory test does use a 30-second call and 90-second permit, but invokes at time zero and only checks that recorded deadlines are positive (`tests/tart_offline.rs:811`). It therefore also passes with the incorrect 90-second bound. A caller could then clone after the 30-second call has expired but before the reservation expires.

   **Minimal fix:** Add a live shorter-call case asserting the exact call deadline in the trace, plus an exact-call-boundary case with a still-live longer permit, asserting `Expired` and preservation of the queued reply. These cases should fail for permit-only enforcement. The existing tests already fail for call-only enforcement; both sides are needed to protect the stated `min` principle.

3. **P2 / should-fix — The reserved-range endpoint test is masked by the redundant broadcast row.** `src/disposable/tart/policy.rs:112`, `src/disposable/tart/policy.rs:113`, `tests/tart_offline/review_fixes.rs:186`. Impact: regression coverage of the new prefix table; no current mask defect.

   **Failure scenario / surviving mutation:** Change `net(240, 0, 0, 0, 4)` to `/5`. This incorrectly admits `248.0.0.0` through `255.255.255.254`, yet every new rejection/acceptance vector and every old rejection vector still has its expected result. The apparent upper endpoint, `255.255.255.255`, remains rejected by the separate `/32` entry. This specific table mutation was checked against the source vectors in memory with Python; Rust tests were not run.

   **Minimal fix:** Assert rejection of `255.255.255.254` and preferably `248.0.0.0`. The explicit broadcast `/32` is wholly contained in `240.0.0.0/4` and can be deleted. Keep the independent reserved-range assertion even if that redundant row is removed.

**Requested checks on the fixes**

The watchdog module is referenced only from the `[[test]]` target at `Cargo.toml:64` and the `mod watch` declaration in `tests/tart_offline.rs:38`. Neither the production library nor executable imports it. No production env/CLI gate, `AdmittedLaunch` mint, or accepting provider was added. The re-exec uses `current_exe()` directly, sets the child mode to one of the two constant strings, passes no caller-supplied arguments, and does not invoke a shell or PATH lookup. Ordinary argument/environment contents therefore cannot select an arbitrary executable or shell command through this wrapper. The child inherits the rest of the environment, but no new interpreter of those values was found in these fixes.

There **is** an ambient selector for the test artifact: `GCU_TART_OFFLINE_CHILD=checks <test-executable>` runs checks without their parent watchdog, and `GCU_TART_OFFLINE_CHILD=hang <test-executable>` enters an unsupervised infinite spin. This follows directly from `watch.rs:29` and `tart_offline.rs:44`. Unknown Unicode values panic before spawning; an invalid-Unicode value is treated as absent. Thus “set only on the re-exec'd child” / “only spawned by the parent” are conventions, not enforced reachability claims. This does not expose a hang mode in the product. For test-runner robustness, an explicit private re-exec argument in addition to the mode would prevent the environment variable alone from accidentally bypassing the wrapper; it would still be a callable internal test entry, not an authentication boundary. Do not add a production token or child-mode API to solve this.

For a normal timeout and successful OS termination, `kill` followed by successful `wait` reaps the immediate child: no zombie remains. The current child checks start no descendants, so process-group/tree termination is not required to reap today's test. The wrapper does not promise tree containment or cleanup if the parent itself is externally killed. Its timeout/error-path qualification is finding 1. This remains separate from any future VM parent-death design.

Normal check exit codes pass through `ExitStatus::code()` to the parent's `exit`; a failed check panics and yields a nonzero status. Signal termination is normalized to 1 (`watch.rs:69`), not preserved as the original signal, which is sufficient for Cargo failure. A timed-out check causes a parent panic rather than passing through the kill status, also correctly nonzero. There is no negative-exit self-test, as noted in the mutation audit. `Command`, `Instant`, `try_wait`, `kill` and `wait` all have Windows implementations; the former non-Unix no-op is gone. Windows runtime behavior was not exercised. `CHECK_LIMIT` is a per-child 30-second limit, not a 30-second limit for the complete parent invocation: the latter also includes the approximately two-second hang self-check, spawn, and cleanup overhead. Avoid reporting the whole target as bounded by exactly 30 seconds.

The IPv4 table contains the expected exclusions for `0/8`, private ranges, CGNAT, loopback, link-local, the conservative special-use /24s, documentation, benchmarking, multicast and reserved space. I found no misspelled network or incorrectly aligned row, and no known missing non-global class in this offline comparison. This is not a live IANA-registry freshness check. Globally reachable special-use examples such as `192.31.196.1`, `192.52.193.1`, and `192.175.48.1` remain syntactically accepted; special-use does not uniformly mean non-global. Unallocated addresses, actual routability, endpoint ownership, gateway exclusion and enforcement are not established by this validator.

All current widths are in `4..=32`. Big-endian construction and `u32::from(Ipv4Addr)` agree; `u32::MAX << (32 - bits)` has no invalid shift for those widths. The `/10`, `/12`, `/15`, `/24` masks are respectively `255.192.0.0`, `255.240.0.0`, `255.254.0.0`, `255.255.255.0`; both `/4` rows use `240.0.0.0`. The unused invalid-width fallback produces a zero mask and rejects everything rather than admitting anything. No current off-by-one mask was found.

Representative results agree with the intended table: `100.63.255.255` and `100.128.0.0` pass while `100.64.0.0`–`100.127.255.255` fail; `172.15.255.255` and `172.32.0.0` pass while `172.16.0.0`–`172.31.255.255` fail; `198.17.255.255` and `198.20.0.0` pass while `198.18.0.0`–`198.19.255.255` fail. Every address in `192.0.0.0/24`, including `.9` and `.10`, is rejected. That conservative handling is documented, although `.9`/`.10` are not direct test vectors; `192.0.1.0`, `192.0.1.255` and `192.0.3.0` pass while `192.0.2/24` fails. `223.255.255.255` passes; `224.0.0.0`–`255.255.255.255` currently fail. Finding 3 concerns mutation coverage, not those current results.

The clone deadline change performs **no new addition, subtraction, duration conversion or saturation**: `min` compares two `MonoInstant` values ordered by their `u64` counts. Construction still uses checked conversion/addition in `deadline.rs:32`; the existing overflow test at `tart_offline.rs:308` protects the shared constructor. The exclusive boundary is enforced by `now >= deadline` before queue consumption (`output.rs:178`). The fake trace receives the same effective instant that dispatch receives (`runner.rs:112`, line 115), and the new shorter-permit tests check it. Trusted same-clock provenance remains the pre-existing caller obligation; no new claim about physical time or cancellation follows from this arithmetic.

The boundary scan is a spelling guard, not Rust name resolution. In particular, **`use std::process as p;` is caught**, because it contains `std::process`; it is not a false negative of the revised helper. Merely adding `extern crate std as s;` need not be rejected, and a later fully qualified `s::process::Command` would still match `process::Command`. However, the following builder constructions contain none of the helper's needles and would escape both current process-construction spelling checks:

```rust
use std::{process::{Command as P}};
// inside a function:
let _ = P::new("sh");
```

```rust
extern crate std as s;
use s::{process::{Command as P}};
// inside a function:
let _ = P::new("sh");
```

```rust
use std::{process as p};
use p::Command as P;
// inside a function:
let _ = P::new("sh");
```

A macro can likewise build `$root::$module::$ty::new("sh")` from an invocation supplying `std, process, Command`, avoiding contiguous forbidden spellings. A builder supplied by another module/dependency need not spell its construction here at all. These are coverage limits, not new builders found in the implementation. The fixtures protect the particular grouped/aliased spelling from round 1; neither scan proves arbitrary expanded Rust has no process construction, no launch mint, or no wait. Parsing comments/literals is also not attempted: legitimate prose such as `// do not use std::process here` or a string containing `process::Command` is a false positive. The new needle broadens coverage without removing the old conditions. The walker's inherited silent IO-error skips still prevent a completeness proof; the integration walk fails on read/traversal errors. No new source-scan weakening was found.

**Deletion/simplicity assessment**

The speculative cross-field digest-distinctness rule and duplicate ledger row schema were deleted as requested. No transport selection, controller, real factory, background thread, or new production lifecycle mechanism was introduced. Keep that scope.

Two further small deletions are justified by redundancy rather than an unproved design: remove the broadcast `/32` already covered by `240/4` (`policy.rs:113`), and optionally remove the separate negative `Copy` assertion machinery (`ledger.rs:130`), since `Copy: Clone` and the negative `Clone` assertion already prohibits both. Keep protection against `Clone`. Neither deletion needs another abstraction. The existing all-zero digest convention is not newly introduced by these fixes and remains data validation, not installation evidence; it is not reopened here.

Real Tart/VM execution, network policy or egress, guest transport, native permissions/Stop, login, and real model evaluation: **NOT_RUN by design**. Acceptance of these offline fixes cannot change those states.
