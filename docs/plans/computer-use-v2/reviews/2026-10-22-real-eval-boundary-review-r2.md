**Must-fix findings**

1. **M1 — High, new: the fake-client exemption authenticates a filename, not the fake implementation.** `src/boundary.rs:30` accepts any regular file named `eval-fake-agent` or `eval-fake-agent.exe`, including a copied real client, a hardlink, or an executable wrapper containing arbitrary code. The test explicitly blesses a regular file containing just `x` (`src/boundary.rs:100`). A copied/wrapped real client at an absolute path with that name and `--driver fake` reaches execution without attestation (`src/main.rs:110`, `src/runner.rs:415`, `src/exec.rs:21`), skips preflight (`src/exec.rs:44`), and omits `--tools` (`src/launch.rs:41`). This reintroduces the exact weaker launch path the change seeks to remove. Rejecting a final-component symlink does not reject symlinked ancestors, hardlinks, wrappers, or replacement between classification and spawn. Even an explicitly attested invocation with that name still gets the weaker policy.

   The genuine fake agent also accepts arbitrary `GCU_BIN` and invokes `call list_apps` / `call get_app_state` **without** `--driver fake` (`src/bin/fake_agent.rs:137`, `src/bin/fake_agent.rs:145`; supplied at `src/launch.rs:89`). Selecting a real gcu instead of `eval-fake-gcu`, or a wrapper at `--gcu`, is not considered by the boundary predicate. Native gcu may independently reject the platform/session/arguments; this review does not claim those calls succeed on every platform. It establishes that eval's fake path does not constrain that executable or force fake driver selection on those calls.

   Require attestation/policy for every arbitrary external executable, or move the no-attestation fake path into a trusted implementation that cannot delegate to arbitrary executables. If a binary exemption remains, bind it to the actual built artifact and execution identity, and constrain the fake backend too. Add negative tests for a regular-file wrapper/copy/hardlink with the exempt name and a genuine fake agent with an external backend.

2. **M2 — High, incomplete new credential validation: validated seed paths can name different bytes at read time, and path exclusion does not establish a disposable identity.** `src/prep.rs:281` checks symlink metadata; `src/prep.rs:293` canonicalizes; `src/prep.rs:297` checks exclusions; then `src/prep.rs:304` reopens the original path with `std::fs::read`. A writer can replace `auth.json`, the seed directory, or an ancestor after validation with a symlink or another file. The subsequent read follows the replacement. It can also become a FIFO or large file, blocking the synchronous provisioning path or consuming unbounded memory before any client timeout exists. Destination `create_new` does not fix source substitution.

   A stable hardlink to a protected auth file passes: it is regular, not a symlink, and canonicalizes to the outside seed path. A bind-mounted alias likewise need not canonicalize to the protected pathname. The synthetic filesystem check confirmed the hardlink predicates and identical inode without touching real credentials. A personal credential copied to an outside directory is also accepted; there is no evidence of evaluation-only identity, expiry, or revocation (`src/prep.rs:304`). Path validation cannot establish that property from opaque contents alone.

   `src/access.rs:148` only enumerates four default dot directories beneath environment `HOME` and `USERPROFILE`. It ignores custom `GROK_HOME`/`CODEX_HOME` and other agent-home overrides, actual OS home when the environment points elsewhere, and this application's credential-bearing independent homes such as `~/.grok-app/agent-home` and `agent-home-official` (repository `docs/llm-wiki/providers.md:20`, `docs/llm-wiki/providers.md:154`). Starting the harness with a scratch `HOME` can therefore hide the operator's real config homes from its denylist. Calling these the complete personal-config exclusions is incorrect.

   Open and validate a bounded regular source through stable directory/file handles, enforce no-follow/ownership/link policy where supported, and copy from that same handle. Include all supported credential-home sources from trusted home resolution. Exclude personal mounts and provision the evaluation identity through the actual external boundary; document what cannot be inferred from a seed pathname. Tests must exercise substitutions and aliases, not only static symlinks.

3. **M3 — High under a writable/shared temp ancestor or permissive umask: exclusive names do not make path-based provisioning private or stable.** `src/prep.rs:97` calls ordinary `create_dir`; 0700 is applied later at `src/prep.rs:105` / `src/prep.rs:215`. With umask 000 the initial mode is 0777, confirmed using a synthetic mkdir. Another user able to observe that parent can plant extra parent-discovered startup material such as `AGENTS.md` during the window. `populate` checks its known child paths, not every possible startup file in the root (`src/prep.rs:171`). There is no such write window if the root is created private atomically.

   The temp parent is taken from ambient temp configuration (`src/prep.rs:125`), checked by pathname, then traversed again for mkdir/chmod/population/cleanup (`src/prep.rs:90`, `src/prep.rs:97`, `src/prep.rs:207`). Swapping a symlinked or otherwise mutable parent after canonical checking can redirect creation into an excluded tree. A replacement after root creation can make chmod/population address a different object. Random naming prevents practical pre-guessing; it does not pin parent or directory identity. A same-user writer also remains unrestricted, as acknowledged in the earlier review.

   Create Unix roots with mode 0700 in the creation operation and use a trusted, stable parent/directory handle for subsequent operations; reject unsupported mutable/reparse/mount cases or require a boundary excluding them. Windows currently has **no** explicit owner-only ACL setup (`src/prep.rs:222`), so private creation there is unverified and must be implemented or real execution disabled on that platform.

   Stable existing `..` paths and ordinary symlink aliases into the listed config roots are resolved by the new canonicalization and are improvements. I found no standalone stable `..` bypass. Case-insensitive filesystem containment is **not established** by `Path::starts_with` after canonicalization (`src/access.rs:176`): the comparison itself is case-sensitive and correctness depends on filesystem-specific canonical spelling. macOS/Windows case aliases and Windows junction/reparse behavior were not run; do not claim a proven case bypass or proven protection without those platform tests. Bind mounts and hardlinks are the separate alias gaps in M2.

4. **M4 — High, still open: cleanup failure changes a row, but does not stop execution or reliably report the leftover environment.** `finish` appends `cleanup_failed` and may downgrade the status (`src/runner.rs:485`), then `run_tasks` unconditionally proceeds to the next task (`src/runner.rs:370`). `run_ab` similarly proceeds through repeats and arms (repository `computer-use/crates/gcu-eval/src/ab/mod.rs:375`). Thus retained auth/state from a failed teardown can coexist with another newly seeded, automatically approved client. This violates the earlier explicit requirement to refuse continuation after cleanup failure.

   There is a second reporting error: if population fails and cleanup also fails, `begin_env` returns `cleanup_failed` (`src/prep.rs:105`), but its caller returns `skipped(... Invalid ...)` (`src/runner.rs:450`); `skipped` sets `env_destroyed = true` unconditionally (`src/runner.rs:541`). No leftover root is supplied to the outcome. Drop may retry deletion, but its error is discarded (`src/prep.rs:46`) and cannot justify a successful cleanup claim. Propagate owned leftover state and a fatal cleanup condition, stop all remaining tasks/arms until cleanup is confirmed, and mark destruction false/unknown on failure. Exercise the complete control flow with injected removal errors.

5. **M5 — High, partial mitigation presented without a full lifetime barrier: a Unix process group is not the complete evaluation tree.** `process_group(0)` is the correct Unix `setpgid` mechanism for the directly spawned child (`src/proc.rs:27`); using `kill(-child_pid, SIGKILL)` targets that group and filters zero/invalid ids (`src/ffi.rs:8`). It does **not** create a new session or prevent a descendant from using `setsid` or `setpgid` to leave. Such a descendant survives timeout and successful parent exit (`src/proc.rs:90`, `src/proc.rs:97`). Windows group cleanup is explicitly a no-op, leaving only direct-child termination (`src/proc.rs:47`).

   The fixture still uses direct-child `kill`/`wait`, not the new group owner (`src/prep.rs:332`, `src/prep.rs:386`); its children survive, and its blocking wait has no deadline. Even the test fixture shell starts `sleep 300` (`tests/lockdown.rs:63`). Native macOS stdio can attach to or launch a Launch Services helper outside the client's group, unchanged from round one (repository `computer-use/crates/gcu-cli/src/runtime.rs:98`, `computer-use/crates/gcu-cli/src/helper/auth.rs:407`, `computer-use/crates/gcu-cli/src/helper/client.rs:173`). Killing the proxy group does not prove the helper's closure, config isolation, approval mode, or lifetime.

   On ordinary timeout, eval waits only for the immediate child, with a two-second best-effort timeout whose result is discarded (`src/proc.rs:93`). Cancellation Drop sends kills but does not wait (`src/proc.rs:54`); `run_one` can then drop the environment guard without confirmed process exit. Tokio may reap the direct child best-effort, but this does not establish deterministic reaping of grandchildren or successful session closure. SIGKILL/OS death of the evaluator runs no Rust Drop at all. Neither process-group membership nor `env_destroyed` proves an orphan cannot retain credentials in memory or open file descriptors.

   Own the desktop/run through an enforceable lifetime mechanism (for example a cgroup/supervisor, Windows Job with kill-on-close and controlled breakaway, or disposable VM), including fixture/helper/leader, and wait for verified teardown before deleting credentials or starting another task. Explicitly fail closed where this is unavailable. Preserve unknown/failed teardown evidence instead of discarding signal/wait errors. This is an existing required boundary, not a claim that process groups alone can be hardened into a sandbox.

6. **M6 — Medium, new process-helper defects: stale group ids and detached pipe readers.** `group.child.wait()` reaps the leader at `src/proc.rs:82`, after which the numeric pid remains stored. `kill_group` runs at `src/proc.rs:97` and again from Drop (`src/proc.rs:54`), after up to two sequential two-second pipe waits. Once that group disappears, the identifier can be reused; a subsequent negative-pid signal can kill an unrelated new group. Timeout also repeats kills after the best-effort wait. Filtering zero does not verify the identity of a recycled group (`src/ffi.rs:12`), and ignoring `kill` errors conceals failures. Avoid blindly re-signalling a reaped process's number; keep a lifetime/identity owner until teardown is complete.

   `take_pipe` moves a `JoinHandle` into `timeout` (`src/proc.rs:109`). On timeout, dropping that handle **detaches**, rather than aborts, its reader task. Cancellation of `run_command` also drops both handles without aborting them. A surviving escaped descendant retaining a pipe writer keeps those tasks/fds alive and can keep them consuming output throughout subsequent tasks. Each reader's byte vector is capped, so a single reader does not allocate without limit; repeated abandoned readers do accumulate capped buffers/tasks over a long-lived runtime. Abort and join readers on timeout/cancellation, and propagate incomplete/read-error capture instead of silently treating every read error as EOF (`src/proc.rs:132`).

7. **M7 — Medium, incomplete new preflight contract: success is reusable for a different launch, and “exact set” is not an unambiguous listing schema.** The key is only the raw client path string, profile string, and model (`src/client_tools.rs:173`). It excludes the gcu executable, real/fake driver selection, config contents, approval policy, startup state, credentials/account/environment, and the identity/content of the client at that path. A library caller can obtain success with fake gcu, then use the same client/model/profile with real driver/gcu and reuse it; `preflight_once` returns the cached success before consulting the new environment (`src/client_tools.rs:204`). Replacing the executable in place also retains success. This is a source-level execution trace, not a performed client run. Removing cross-environment success caching is safer than pretending a pathname is immutable provenance; otherwise key and bind all effective launch-policy inputs without logging credentials.

   `tool_names` prioritizes `tools` and ignores `text` (`src/client_tools.rs:273`). The following contradictory value is accepted by inspection:

   ```json
   {"tools":["list_apps","list_windows","search_tool","todo_write","use_tool"],"text":"shell and read_file are enabled"}
   ```

   The `text` fallback discards all non-ASCII words and uses a set, ignoring duplicates (`src/client_tools.rs:157`, `src/client_tools.rs:262`). For example `{"text":"不可用：list_apps、list_windows、search_tool、todo_write、use_tool"}` says the tools are unavailable but passes token-set equality. Arbitrary ASCII prose such as `ok` now fails; that specific hole is fixed. Require one explicit schema for the advisory listing and reject contradictory fields/non-list text. This still cannot turn a model assertion into trusted verification.

   The five-name constant is not a demonstrated full effective inventory. It intentionally omits tools actually present in the minimal gcu catalog, and stays identical for full profile (`src/client_tools.rs:23`; repository `computer-use/crates/gcu-mcp/src/catalog/profiles.rs:7`, `computer-use/crates/gcu-mcp/src/catalog/profiles.rs:37`). It may describe a client's lazy discovery entry, but no pinned client source/offline evidence establishes that interpretation, naming, or removal of other dispatch targets. A truthful exhaustive MCP inventory can therefore be rejected while a synthetic five-name response passes.

8. **M8 — High, earlier proof requirement still open: the client can execute before any trusted policy check.** Preflight is itself `--always-approve` with seeded auth and a live MCP config (`src/client_tools.rs:223`, `src/exec.rs:34`, `src/exec.rs:48`). Neither invocation selects a verified restrictive sandbox, disables executable hooks/plugins/compat imports, isolates a backend/leader, or verifies an effective MCP set (`src/launch.rs:24`, `src/launch.rs:128`). There is no client digest/version pin or offline test of denied direct dispatch and `search_tool`/`use_tool` resolution. Fresh directories and a model response do not fill this gap. The repository's App code even has explicit compatibility-MCP disablement that this generated config lacks (repository `src-tauri/src/agent_home_config.rs:231`); this is evidence to investigate, not proof that the current isolated launch imports a personal catalog.

   Pin the supported client and verify those policies from trusted source or a model-free offline dispatcher/startup test before supplying credentials. Keep execution disabled if the effective policy cannot be established. The new attestation text correctly admits the absence of an OS sandbox, but the flag does not supply the missing technical evidence for earlier §7 item 3.

9. **M9 — Medium, earlier reporting/leak requirement still open: unknown telemetry is represented as empty/zero, and cooperative logs remain an unsanitized reporting channel.** `read_side` treats a missing/unreadable log as empty (`src/exec.rs:206`), `read_calls` does the same (`src/exec.rs:275`), and `judge` accepts an empty network vector as no forbidden network effect (repository `computer-use/crates/gcu-eval/src/oracle.rs:290`). These are not OS process/network monitors. A pass can carry zero tool calls and zero unknown calls when no tool-call telemetry was collected (`src/exec.rs:92`, `src/exec.rs:117`); a row's unobserved calls are not a measured zero. Reports serialize neither attestation/driver/MCP/client policy provenance nor telemetry availability (`src/report.rs:73`). A separate desktop `not_run` row and prose warning do not identify the assurance of a successful task, and A/B suppresses that desktop row.

   The preflight's former `shell_SENSITIVEVALUE` failure-reason leak is fixed: all normal failure labels are fixed strings or canonical constants (`src/client_tools.rs:247`, `src/client_tools.rs:289`). Shim argument logging is also fixed for normal fixed-name invocations (`src/prep.rs:242`, `src/prep.rs:255`), and client result conversion retains only numeric usage/turn fields (`src/exec.rs:392`). I found no new direct model-text/proxy-value serialization in those paths.

   However, a launched process can write arbitrary JSON to its supplied `GCU_EVAL_TOOL_LOG`; `read_calls` accepts the raw `tool` string and `fill_calls` copies it to outcomes (`src/launch.rs:81`, `src/exec.rs:282`, `src/exec.rs:317`). A line such as `{"tool":"read_file_SENSITIVEVALUE","result":"ok"}` puts that value into JSON and HTML (`src/report.rs:85`, `src/report.rs:137`). HTML escaping prevents markup injection, not disclosure. This log channel predates the patch; it remains open under the requested “never retain credential-bearing payloads” criterion. There is also no size bound on the state/tool/side/transcript file reads (`src/exec.rs:199`, `src/exec.rs:206`, `src/exec.rs:232`, `src/exec.rs:275`), despite the new pipe bounds. Reject oversized files and canonicalize/report only recognized tool identifiers; count unknown names without copying their bytes. Preserve unavailable telemetry and unverified confinement explicitly. Proxy credentials still enter recognized real-client environments verbatim, now also on fake-driver external-client launches (`src/launch.rs:108`); their propagation to MCP/client-owned logs is unverified, not established safe by report filtering.
