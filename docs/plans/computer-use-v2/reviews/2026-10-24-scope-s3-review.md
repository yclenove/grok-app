**Must fix**

1. **[P1; (a)(2)/(4)] Old connection work can acquire the rebound generation.** `gcu-cli/src/scope/data.rs:84` passes the mutable lease to MCP, while the connection's captured `AttemptAuthority` guards only the outer socket future at `:104`. rmcp 3.5.1 spawns request handlers separately; those handlers do not inherit that authority. Schedule: accept under generation 1; queue a handler (or a script worker's next `cu.app` operation); process Rebind to generation 2; poll the already-ready handler before `serve_one` observes `authority.changed()` and closes the session. The handler can open generation 2 and read its newly admitted target: `gcu-core/src/action/observe.rs:66` falls back to the current lease, and `gcu-cli/src/script_worker.rs:195` dispatches without the connection epoch. Closing the socket later, or scrubbing the final MCP result, does not undo that read or a completed delivery. Carry and enforce the original authority in every spawned handler and nested script operation. Add a bounded dispatch/rebind barrier test asserting zero reads/deliveries from the old connection, including replies to the script worker.

2. **[P1; (a)(4)] Expiry is a watcher callback, not a condition of usable authority.** `gcu-cli/src/scope/state.rs:73` checks the clock only through control-frame application; `gcu-cli/src/scope/mod.rs:120` supplies the asynchronous expiry timer. The deadline never reaches S1: `ScopeLease::arm_attempt` (`gcu-core/src/scope/authority.rs:66`) and `commit_if_current` (`gcu-core/src/scope/commit.rs:38`) accept an Active record without checking time. Schedule: stop renewal; the monotonic deadline passes; a ready MCP handler runs before the timeout task is polled and performs discovery/read or commits a response. It still receives valid authority. The outer biased select does not give the watcher priority over independently spawned handlers. Enforce the engine-owned deadline at authority use and publication as well as retaining the teardown timer; Renew must update that same deadline. Test an actual data operation after clock expiry while watcher polling is held back, rather than awaiting eventual teardown.

3. **[P1; (a)(4)] Revocation can leave model script execution alive after engine exit.** The new scoped assembly enables the process runner at `gcu-cli/src/scope/data.rs:85`, but `gcu-cli/src/script_worker.rs:209` kills/reaps its child only after the awaited loop finishes; dropping the future has no child-owner cleanup. Schedule: on a Unix build with `script`, start `computer_script` with a 30-second pure JS loop, then send Revoke or close control. `gcu-cli/src/scope/mod.rs:96` drops the data future and returns; runtime shutdown drops outstanding tasks and exits. Dropping `std::process::Child` does not kill the worker. Its parent watchdog disappears, and its own interrupt checks only its original timeout (`gcu-script/src/worker.rs:186`, `gcu-script/src/runtime.rs:413`), so it can continue for the remaining script horizon. `gcu-eval/src/scope/mod.rs:218` waits only for the engine and can report teardown complete meanwhile. Give script children cancellation-safe ownership and bounded kill/reap, including parent death. Test the actual worker PID and require its exit before the supervisor's cleanup barrier succeeds.
