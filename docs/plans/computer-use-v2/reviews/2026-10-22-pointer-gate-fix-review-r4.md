## Must-fix — new implementation defects

### N1 — Medium: full desktop/security/COM validation scales with every targeted event

`W/input/admission.rs:157` invokes full `validate()` inside the event loop. The production closure at `W/input/ffi/mod.rs:463` enumerates the entire desktop, validates the stamp/frame/scale, runs two `WinGate` checks and two virtual-desktop queries, and allocates a scalar snapshot that is immediately discarded (`:151`, `:165`, `:185`, `:217`). Enumeration also walks each visible window's children and opens processes for creation times (`W/ffi/windows.rs:111`, `:126`), so this is desktop-wide work per posted event, including Unicode up events that produce no `WM_CHAR`.

One 256-unit text packet contains 512 events (`W/input/messages.rs:13`, `:85`, `:89`), hence 512 full validations in its native send instead of one. An 8192-unit request needs 16,384 full validations; the supported 65,536-unit ceiling needs 131,072 (`W/input/text.rs:8`). With the 4750ms driver deadline and 110ms cleanup reservation (`W/input/mod.rs:151`), even the optimistic 4640ms budget allows only 0.283ms/full validation at 8192 units or 0.0354ms at the ceiling, before discovery, parent acknowledgements, posting, or settling. Actual latency was not measured here, but the multiplication is deterministic and newly introduced. On sufficiently populated/slow desktops this converts a valid targeted typing request into partial text followed by timeout; cancellation checks prevent further posts but do not recover the requested text.

**Required:** bound the heavy work and retain native-thread recipient validation. A full preparation once per existing bounded packet, followed by request and scalar stamp/ancestry/TID/PID/class/geometry/DPI checks immediately before each post, preserves M1's protection against substitution between caller validation and dispatch, and between events. Use a targeted variant without the foreground requirement; retain the nonempty generation marker on the real adapter. Keep full checks outside the ledger. Merely deleting all later checks or relying on the caller's earlier validation would regress M1. This alternative preserves the restored recipient guarantee, not an assertion that every mutable security/desktop property is freshly queried per event; any stronger freshness contract needs explicit invalidation or bounded refresh. Add a meaningful validation-count regression and native long-text timing at representative desktop sizes, rather than deferring this cost to unspecified future tuning.

### N2 — High: the new probe's “stable landing” can be an early transient, and no landing can still count as valid

`WT/contract/landing_probe.rs:403` returns the **first** pair of equal samples away from the park position. It never checks subsequent samples or requires agreement with the end of the 50ms observation. At `:459` that early pair supplies all histogram deltas; the remainder of the trace is discarded. A synthetic sequence `park → P at 0.5ms → P at 1ms → Q at 20ms → Q at 49.5ms` reports P and 0.5ms. If P is the inverse prediction, the histogram can report zero error despite a different final position Q. No target/order/raw samples are emitted to diagnose it.

If every read remains at the park position, `stable_landing` returns `None`; `:462` instead uses the last sample and increments `unstable`. Yet `valid_reads` at `:483` subtracts only completely unreadable moves, and `:525` ignores `unstable`. Thus 400 accepted `SendInput` calls and parked-only traces can satisfy every live-test assertion (`WT/contract/live.rs:775`). This fixes the zero-read vacuity but still permits zero confirmed target landings. A successful measurement test intentionally need not mean zero mapping error; nevertheless, it must distinguish a measured landing from an unapplied, clipped, or inconclusive move.

**Required:** retain per-move requested/normalized coordinates, the park position, time origin, samples and terminal position. Record first arrival within the production 15ms budget separately from the later stable position; reject or explicitly mark inconclusive no-departure/unstable/incomplete traces, and do not include those in successful-landing counts. Validate stability against the tail of the observation, not just the first equal pair. Keep nonzero-error data available for diagnosing the mapping rather than hiding it with tolerance. Cover the transient-P/final-Q and parked-only sequences before hardware collection. A raw `SendInput` sampler still needs a separate run through the actual production gate/settle path before it proves production timing.

### N3 — Medium: bounding-box targets mix monitor-gap clipping into normalization error

`WT/contract/landing_probe.rs:250` accepts coordinates using only the virtual desktop's bounding rectangle. `build_targets` receives monitor rectangles but uses them only to generate axis edges (`:259`); its random fill at `:281` never checks membership in a monitor. `park_corner` likewise chooses bounding-box corners (`:359`), some of which may be off every monitor.

A local translation of the exact target generator for monitors `(0,0)-(1920,1080)` and `(1920,0)-(4480,1440)` produced **400 targets, 31 in the bottom-left monitor gap**, including `(1167,1252)` and `(1259,1360)`. Those pixels cannot be normal on-screen cursor landings. Depending on Windows cursor constraints, they yield clipping/projection or no departure, but are fed into the same “inverse error” histogram and successful-read count. Printing topology does not distinguish those rows after the per-move data has been discarded. An invalid parking corner can also make the distance test abort even when another on-monitor parking location is available.

**Required:** select and park on the union of active monitor rectangles. If gap/clip behavior is intentionally measured, label it separately and exclude it from normalization acceptance. Preserve quantization-disagreement coverage at reachable pixels; if a disagreement axis coordinate has no pixel on a selected midline, choose a containing monitor's other-axis coordinate. Fail or restart when topology/clip constraints change during collection, so one fixed metrics snapshot is not silently applied to a different desktop.

## Gate-call, compatibility, and build audit

**Hung target and allocations.** `GetPropW`, `GetDpiForWindow`, `GetWindowRect`, `IsIconic`, `GetClassNameW`, and `GetWindowThreadProcessId` query USER/window metadata. The new calls do not use `SendMessage`, call the target window procedure, enumerate windows, open processes, or invoke COM (`W/input/ffi/native.rs:31`, `:40`, `:51`, `:55`, `:60`). In particular, `GetPropW` does not ask the target app to provide its property, so a hung message pump is not a target-response wait. Class comparison now uses a fixed 256-unit stack buffer and prepared UTF-16 (`:35`); property-name allocation happens before the gate (`W/input/ffi/mod.rs:217`). These are bounded-work metadata checks, **not a hard wall-clock guarantee** against OS locks, scheduling or kernel stalls. No hung-window timing experiment was performed.

The successful admission path adds no heap allocation. Strictly, the rect failure path still constructs a small error string (`W/input/ffi/native.rs:43`; `W/input/ffi/mod.rs:74`) before converting it to `None`; it is not entirely allocation-free on failure, but this is not desktop-size allocation or blocking validation. New diagnostics use a constant-initialized thread-local `Cell`; production dispatch flushes after ledger release (`W/input/admission.rs:100`, `:129`), while probes flush after mutex release (`W/input/hook_probe.rs:73`). Acquisition timing now measures only the wait (`W/input/hook_probe/gate.rs:278`), not admission and settle. No new heavy successful-path work inside the acquired gate was found.

**Rect/DPI source and ordinary refusals.** Enumeration uses `GetWindowRect`, not DWM extended frame bounds (`W/ffi/windows.rs:88`, `:141`). The new snapshot reuses that API and checks the identical integer-to-`f64` rect representation (`W/input/ffi/mod.rs:135`, `:199`). The worker enters PMv2 before both reads (`W/ffi/mod.rs:57`, `:75`). Invisible resize borders and mixed DPI therefore do not themselves create a new source mismatch. Enumeration and preparation also use the same `GetDpiForWindow` and DPI/96 calculation (`W/ffi/windows.rs:127`, `:147`; `W/input/ffi/mod.rs:141`). A real move, resize, minimize or DPI transition can refuse an otherwise legitimate action, including a keyboard action; that is the intended stale-snapshot behavior. Unchanged windows have no identified systematic false refusal from these comparisons. The checks are sequential reads, not an atomic OS snapshot.

**Generation-property semantics.** The target app does not need to create this property. `RealWinApi` exposes its own NUL-terminated name (`W/ffi/mod.rs:128`, `:162`); enumeration installs its generation value with `SetPropW` when absent (`W/ffi/windows.rs:93`). Normal actionable targets therefore already have it when validation snapshots `HwndStamp.created`. A property removed/replaced after enumeration is correctly refused; recreation during a later enumeration yields a new stamp and rejects the old target. An elevated discovery-only window may have a zero marker, but `WinGate` already refuses action on it. The default empty-name trait implementation (`W/api.rs:85`) skips scalar generation checking for adapters that provide no marker; the real adapter does not use that fallback. No “all third-party apps lack this property, so all input fails” defect was found. The property is a reuse marker, not authentication against another process that can alter window properties.

**Test-name injection and production.** All three public helper entry points require `windows && test-support && !test` (`W/input/mod.rs:39`, `:52`, `:59`); the override storage, lookup and setter themselves are feature-gated within the Windows non-test module (`W/input/hook_probe/gate.rs:199`, `:203`, `:215`). There is no new environment-variable name override. `test-support` has no default activation (`computer-use/crates/gcu-driver-windows/Cargo.toml:8`), normal workspace dependencies do not enable it, and the release build command does not enable it (`.github/workflows/release-computer-use.yml:132`). **Absent from the configured production build: yes. Absent from every possible release build: no.** Explicit `--features test-support` or `--all-features` includes the name injector even with optimizations; `not(test)` does not exclude it from a normal dependency build. No unintended activation was found, and this review does not claim binary inspection.

**Workflow.** YAML parses locally. Both new steps have `runner.os == 'Windows'`, inherit `working-directory: computer-use` (`.github/workflows/computer-use.yml:44`), and select the declared package, feature and integration target. `clippy --all-targets` includes that feature-required target and the Windows contract probe compilation. Commands use `--locked`; the existing checkout/cache SHA pins remain unchanged (`:48`, `:61`), and the toolchain remains pinned to `1.99.0` in `computer-use/rust-toolchain.toml:4`. No new action/pin, shell interpolation, working-directory or step-syntax defect was found. The kernel tests do not require interactive input; the ignored landing measurement remains outside this CI invocation by design. Actual compiler/clippy/test results must come from Windows CI.
