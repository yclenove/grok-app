**Verdict: MERGE-AFTER-FIXES. Do not run these commits on the shared Mini as-is.**

Independent CODE review, round 1 of at most 3, of `cu2/s11-m2c`: `b41f3e5a` and `d46c1a19` over `25bf6433`. File references below are relative to `computer-use/`. Reviewed against ADR 0019 §2, §5 C4/C9, and the S11-0c/virtiofs facts. The controller's measured macOS 27 command and output shapes are accepted as facts; this review makes no new Mac measurements.

Read-only except for this report. No network, Cargo, test-suite execution, disk/VM operations, source edits, or commits. Both shell files passed `bash -n`. Additional checks evaluated the existing shell functions in memory with IO boundaries replaced by functions returning synthetic values; they created no scratch files. The full suite was inspected, not run, because it writes scratch files and launches helpers.

The findings below are must-fix for host safety, boundedness, or silent measurement errors. They do not require implementing the deferred C5–C10 experiments or a production volume manager.

1. **P1 — Fresh verification does not bind the subsequent detach to the verified attachment.** `scripts/s11-0-probe.sh:1685`, `:1687`, `:1692`, `:1693`; `docs/s11-0-probe-runbook.md:118`, `:134`.

   **Failure scenario:** `info_holds` correctly verifies this image, its recorded dev/inode, `/dev/disk4`, and its mountpoint. Another disk operation then detaches it and attaches someone else's disk as `disk4` before `hdiutil detach /dev/disk4` executes. The script detaches the replacement. The same window exists before force-detach. Fresh queries and randomized filenames do not prevent device-number reuse. The runbook's notice reserves no exclusive disk/path-operation window, and the program requires no receipt establishing one.

   **Minimal fix:** enforce the ADR §2 destructive-rule-1 lab precondition: a controller-held, recorded exclusive window covering disk attach/detach, hotplug, and replacement of the target paths from verification through completion. Refuse destructive argv if that condition cannot be established or is lost. A lock among this script's own instances alone does not establish it. Alternatively use an operation whose attachment identity is proven to remain bound at effect time; no such primitive is demonstrated here. Keep both fresh checks, including the one before the sole force attempt.

2. **P1 — Directory deletion has no recorded parent/child identity, and quarantine loses the original recovery evidence.** `scripts/s11-0-probe.sh:1620`, `:1635`, `:1592`, `:1598`, `:1673`, `:1810`, `:2077`; `docs/s11-0-probe-runbook.md:130`, `:132`.

   **Failure scenario:** after detach, another process moves the original empty underlying mount directory aside and installs a different empty directory at the same name. `unlink_image` checks only the image's dev/inode, then removes that replacement directory and potentially a replacement attempt directory. Neither M₀ nor A has an identity to compare. Earlier failure branches also run pathname `rmdir` without one. A symlink in an ancestor can redirect these lookups; the final image `! -L` check does not protect its parents. `--out` ancestry/ownership/ACLs are not validated for stage V. This violates “remove only what this attempt created” even when the image check succeeds.

   Recovery has a related concrete gap: `attach.plist` and the original dev/inode/device exist only in shell variables or `$WORKDIR`. The finalizer deletes that scratch directory, while `write_vol_meta`/`save_stage_v` omit these identities. The runbook tells the operator to compare against recorded attach and report values that are no longer available. Re-reading today's path cannot reconstruct the original identity after replacement.

   **Minimal fix:** record and retain identities for the trusted root, A, I, and the underlying M₀ when created, distinguish M₀ from the mounted root, and verify them through trusted no-follow parent FDs before each unlink/rmdir. Reject unsafe ancestry and replaced parents/children; quarantine without a pathname cleanup fallback. Persist a small recovery receipt outside the exported volume and disposable scratch before proceeding, including original image dev/inode, normalized device, mountpoint, and lifecycle state. Apply these checks to failed-create and partial-setup cleanup too. Use the exclusion condition in finding 1 for the remaining check-to-effect window.

3. **P1 — Failed extraction is treated as end-of-array, allowing false attachment absence.** `scripts/s11-0-probe.sh:1382`, `:1429`, `:1436`, `:1442`, `:1455`, `:1465`, `:1478`, `:1651`.

   **Failure scenario:** `hdiutil info` contains an ordinary unrelated image at index 0, another image whose path contains a literal `$` at index 1, and this attempt's still-attached image at index 2. `pl_get` rejects the valid index-1 path at `:1382`. `info_absent` treats that failure as array termination and returns success because it saw index 0. If attach took effect but returned nonzero, `:1651` then unlinks the live image. The mounted-directory `rmdir` may fail afterward, but the unsafe unlink has already happened. A missing/wrong-type path in a later dictionary has the same effect. `info_holds` likewise accepts a match followed by failed extraction; its entity loop also has no overflow rejection at eight entries.

   In-memory evaluation of the actual `info_absent` returned **0** for unrelated `[0]`, failed extraction `[1]`, live owned `[2]`. `info_holds` returned **0** for a match followed by failed extraction. A changed image inode correctly returned **1**, so the existing inode comparison is useful; the parser is the problem. Ordinary truncated XML is not automatically accepted: failure at the first entry reaches the empty-array/lint check. The unsafe case is accepting a successfully read prefix as a complete inventory.

   **Minimal fix:** validate the whole plist and its bounded array lengths/types first, then require successful extraction of every required entry. Distinguish an authoritative array length from extraction/validation failure. Reject overflow, missing fields, conflicting mappings, and incomplete enumeration. Absence requires a complete validated inventory, including an explicitly empty array. Do not interpret unusual path bytes as end-of-array; paths remain data in independent argv arguments. Parsing uncertainty must quarantine before detach/unlink.

4. **P1 — Volume filesystem IO can block the controller outside the bounded runner; cleanup has no absolute end.** `scripts/s11-0-probe.sh:915`, `:1662`, `:1730`, `:1745`, `:1596`, `:1598`, `:120`, `:129`, `:483`; `tools/s11-mailbox-probe/src/io.rs:508`.

   **Failure scenario:** after attach succeeds, opening/writing `.metadata_never_index`, or creating/seeding the mailbox on HFS, blocks in filesystem IO. These operations execute synchronously in the controller, so no timeout loop can run. The `-f`/`-L` checks before the bounded result reads can also block before `head` is started. Raw `rm`/`rmdir` effects are outside supervision. A tool-specific timeout therefore does not establish the requested no-hang property for the volume attempt.

   The system-tool invocations themselves do go through `vol_run`/`run_bounded`, use `/dev/null` stdin, cap accepted output, and avoid unconditional waits on jobs still listed as running. That is useful containment for a hung or interactive `diskutil`. However, cleanup uses a decrementing `CLEANUP_LEFT`, not an absolute cleanup deadline; `reap_ssh_bg` and synchronous parsing/IO are not charged to it. Per-command timeouts also start their TERM/KILL/reap grace after the requested command allowance. There is no shared ≤40-second volume-preparation end; repeated five-second plist queries can consume much more of the global 1500-second allowance.

   **Minimal fix:** put volume filesystem opens/writes/queries/deletions in supervised workers, ideally the same small FD-based helper needed for finding 2. Establish absolute phase/load/cleanup ends and clamp every command plus termination/reap to the remaining allowance. Preserve the tighter aggregate cleanup allowance if desired; do not reset it to extend a run. A worker that cannot be confirmed exited means quarantine and no later effects. Guest `create_exclusive` also performs blocking write/fsync without a deadline parameter: its `Instant` checks bound iteration admission, not a stuck syscall. Keep an external attempt/VM termination bound covering that case rather than claiming the guest timer alone is a hard limit.

5. **P1 — The host-space reserve is never checked, so C9 can fill the backing host and call it a successful capped-volume result.** `scripts/s11-0-probe.sh:1628`, `:1717`, `:1719`, `:1773`, `:1788`, `:1793`.

   **Failure scenario:** only a few MiB remain on the host filesystem. The sparse image creates and attaches, then growing it exhausts host space before its HFS filesystem is full. If the backing-store failure reaches the guest as ENOSPC, C9 accepts it: image sizes remain below 80 MiB and host free-space loss approximately equals image growth. There is no ≥256 MiB preflight from ADR §2, no minimum in `measure_now base`, and no check of whether the recorded HFS free-space observation contradicts volume exhaustion. The first host-space measurement is after image preparation and VM setup, so it also misses their consumption.

   In-memory `judge_c9` accepted **ok** with ENOSPC, about 8 MiB of image allocation/host loss, and **48 MiB still free in the HFS filesystem**. This checks acceptance logic, not which errno a real exhausted backing store will return.

   **Minimal fix:** obtain a bounded host-free-space observation before create and enforce the ≥256 MiB reserve, with another check before the fill workload. Record the initial capacity/allocation/host-space observations. Treat backing-store exhaustion or an ambiguous ENOSPC origin as unknown/failed, not a volume-capacity pass. Use the observed volume/host free-space evidence to distinguish these cases; do not assume every guest ENOSPC proves the dedicated filesystem filled.

6. **P2 — C4 reports unobserved sizes as zero and can pass without observing the filesystem name or size cap.** `scripts/s11-0-probe.sh:1495`, `:1500`, `:1610`, `:1642`, `:1827`, `:1817`.

   **Failure scenario:** a C4 run completes create/attach/detach. `stat_image` obtained real size/block values, but `volume_up` saves only dev/inode. Only C9 calls `measure_now`. C4, C1, and C2 therefore serialize `image_bytes=0` and `image_alloc=0`, despite a nonempty image. C4 can become `ok/volume-ok` with `capacity=unknown`, and never checks the live-image 80 MiB cap. The measured `filesystem-name=Case-sensitive HFS+` field is never read; generic `hfs` and `Apple_HFS` do not establish case sensitivity. Missing readback is being mixed with apparent positive measurement.

   An in-memory call to the existing `finish_c4` produced **ok**, size/allocation **0**, and capacity **unknown** after a successful cleanup state.

   **Minimal fix:** record actual image logical/allocated sizes from the first successful stat for every V case, enforce the cap before use, and retain later observations where applicable. Initialize unobserved metrics to an explicit unknown value, not zero. Read and report the measured filesystem-name field, with a fixed mapping if a token is needed. Define C4's coverage honestly: unknown required filesystem/capacity evidence cannot produce a complete C4 pass. Indexing/backup states may remain observed `enabled`/`included`/`unknown`; do not invent successful exclusions.

7. **P1 — C9 forgets observed peaks and permits unexplained host growth inside an implicit 1 MiB allowance.** `scripts/s11-0-probe.sh:1720`, `:1722`, `:1765`, `:1778`, `:1783`, `:1798`; `tools/s11-mailbox-probe/src/run.rs:352`.

   **Failure scenario:** a progress sample observes image logical/allocation size above 80 MiB. `measure_now sample` merely overwrites the current fields. Subsequent measurements replace them, and `judge_c9` checks only the final values. The guest can remove a last payload file to make space for its result, and host free space can recover for other reasons. An observed violation can disappear into `ok`; the report contains no maxima or sample count. The same problem applies to a transient excess host-space loss.

   The in-memory check seeded an earlier 90,000,000-byte observation and then supplied an 80,000,000-byte final observation: verdict **ok**. A separate check with allocation growth **1,000,000** and host loss **2,000,000** also returned **ok**, because `growth + 1048576` allows additional unaccounted storage. The requested criterion does not authorize that unexplained allowance. ADR §5 permits separately declared bounded receipts, not an undisclosed exemption for arbitrary growth.

   **Minimal fix:** retain and report observed maxima and sample count from preparation through completion; make any observed cap violation sticky. Judge both maxima and final evidence, and keep incomplete coverage explicit. Compare host-space loss against image growth plus only separately identified, measured/declared bounded overhead; otherwise return unknown/failed. Sampling must remain labeled sampling and cannot prove absence of unobserved peaks or all APFS COW/snapshot effects.

8. **P2 — C9 accepts an incomplete/contradictory terminal record and ignores several guest failure states.** `scripts/s11-0-probe.sh:1746`, `:1751`, `:1753`, `:1760`, `:1804`.

   **Failure scenario:** the result contains `enospc=0 enospc=1`; the last token wins and C9 can pass. A valid first line followed by extra non-newline bytes, including an oversized tail beyond `head`'s cap, is also accepted: one newline is counted, but whole-record consumption and the cap+1 overflow condition are not checked. The shell reader does not verify same-FD regular-file/nlink/device/name binding. These are guest-controlled bytes, unlike the system plist. Separately, after a plausible record is published, the guest/dispatcher can exit nonzero or SSH can fail; `m_run_c9` checks only `G_TO` and `G_RU`, unlike the completion checks reused for C1/C2. The row can still become `ok`.

   **Minimal fix:** require a unique, complete closed record with exact version/op/role/mode binding, no duplicate fields or trailing bytes, and explicit cap+1 rejection. Read through the existing safe FD machinery or a bounded helper with the same guarantees. Require clean guest completion and accepted diagnostic/output bounds; a result file does not erase nonzero/aborted/overflowed execution. Preserve the result as a provisional observation when execution completion is unknown.

9. **P2 — The full-volume result fallback changes reported counts without confirming removal or publication.** `tools/s11-mailbox-probe/src/fill.rs:122`, `tools/s11-mailbox-probe/src/run.rs:352`, `:354`, `:357`, `:360`.

   **Failure scenario:** ENOSPC is reached and storing the terminal record fails. `remove_last` discards an unlink error, but `c9_fill` decrements files and bytes unconditionally. If unlink fails transiently and the subsequent record write succeeds, the published count is wrong. If the second publication fails, the process still returns zero whenever ENOSPC was observed or any file was written. This is inconsistent with the documented successful-publication/unknown behavior and complicates distinguishing a complete measurement from a partially published observation.

   **Minimal fix:** return and check removal success; adjust live-file/byte counts only after confirmed removal. Distinguish cumulative bytes written from remaining payload if both are reported. Check the final store result and return nonzero on failed publication or an expired completion deadline. ENOSPC may remain an observed fact, but it must not manufacture successful terminal delivery.

**Test assessment and three mutations the suite would miss**

The stubs accurately encode the measured create/attach argv, bare attach versus prefixed info device names, hfs mount flags/owners, the warning, eject text, and unsupported `diskutil image info`. However, `#s11plist` plus flattened key/value lines is not a real plist fixture: it does not exercise XML/type/array completeness or external-entity behavior. The simulated image is a zero-byte file with constant synthetic dev/inode and size/blocks; detach is a filesystem simulation. `c9write` directly plants `enospc=1` and does not execute Rust fill or grow the image. Thus passing tests cannot validate volume identity, actual full-volume behavior, or host-space accounting. `stat_big`, `df_drop`, `c9_no_enospc`, and `fail_force` switches exist in the stubs but are not selected by the suite.

These are source-based mutation predictions, not claims of an executed mutation run:

1. Delete the dev/inode equality checks in both `info_holds` and `unlink_image`. All volume fixtures continue returning dev=11/ino=22, so no assertion distinguishes the missing checks. Add image replacement and parent/mountpoint replacement fixtures, with canaries proving no effects on the replacements.
2. Delete the second `info_holds` check immediately before force-detach, retaining the normal pre-detach check. The force test has a permanently stable mapping, and the mismatch test changes the mapping before normal detach. No fixture changes device/image/mount identity between a failed normal detach and force. Assert zero force calls in that window.
3. Replace `info_absent` with unconditional success. Normal stub detach always removes its attachment, and there is no failed-attach-with-live-attachment or retained-attachment-after-success fixture. The existing mismatch/timeout/incomplete tests fail earlier and still quarantine. Add a valid plist with unrelated entries, a failed required field in a later entry, and the owned attachment after it; also simulate detach success with an attachment still present. Assert no unlink/rmdir and a nonzero quarantine result.

Use actual plist bytes with an independent bounded parser in these tests. Also cover capped/unknown observations, backing-host exhaustion, an over-cap sample followed by an under-cap final observation, malformed C9 records, and failed terminal publication/removal. These are boundary checks, not more success-path copies.

**Size/simplicity:** the shell diff adds 694 lines and removes 27. Keep the existing orchestration rather than introducing another lifecycle framework. Delete duplication by parameterizing the common case-row JSON writer in `save_stage_m`/`save_stage_v`; sharing the measured-case setup/launch/measure/cleanup sequence in `run_m_one`/`run_v_one`; and using one bounded per-attempt driver for the C2/C9 boundary loops and explicit skipped rows. Declare volume defaults once instead of repeating them at global scope, `reset_vol`, and report decoding. Most importantly, replace the repeated partial `plutil` array walks with one small complete parser/identity helper, and use that same boundary for FD-based checks. Simplification is advice, not an additional merge blocker; none of it should remove the safety checks identified above.
