**R3-1 — P2: the shared read end is checked only at retry entry, so the stable final try can finish after it**

Evidence: `tart/mailbox/slots.rs:671` checks `clock.now()` once at the top of each iteration. Metadata/preflight, the actual read (`:770`), and stability validation (`:780`) have no further end check; the stable path returns success at `:794`. `poll_guest_until` then calls the mutating `tracker.observe` at `:465`. The new helper documents its shared deadline as covering every try, including the stable frame (`:342`), but expiry during that final try is only noticed if replacement forces another iteration.

Counterexample: use a valid inventory terminal and the existing `IoPoint::AfterRead` hook to advance the clock to `end`, leaving the file unchanged. Stability succeeds, the reader returns the frame, and the tracker records the terminal despite the exhausted read end. The supplied deadline regressions advance time **and replace the file** (`tart/mailbox/tests/slots.rs:372`; `tart/mailbox/tests/guest_sim.rs:1309`), so they exercise the next-iteration check only. This finding concerns the new M4a reader's shared end; whole-machine late-result handling remains M4b work under the unchanged v1 pre-dispatch contract.

Minimal fix: recheck the shared end immediately before the byte read and after stability validation, returning nonsticky `Deadline` with the accumulated bytes before observing the frame. Add the stable-file variant: expiry reports all read bytes, leaves sequence state unchanged, and a later call with a fresh end can deliver the same terminal once. This rejects late results without claiming that synchronous filesystem calls can be preempted.

**R3-2 — P2: a partial physical read followed by an IO error loses its bytes**

Evidence: `tart/mailbox/sys.rs:142` returns `Result<Vec<u8>, SysErr>`. Its loop can read some bytes, update `filled` (`:157`), then return through `?` on a later failed `libc::read` (`:152`), discarding the partial count. The new caller wraps that error with only the bytes charged by **previous** iterations (`tart/mailbox/slots.rs:769`); it cannot include the bytes already read by this failing iteration. `MailboxGuestChannel::account_failed` consequently understates its attempt total (`tart/mailbox_guest.rs:144`).

For example, a 4096-byte regular slot yields 1024 bytes followed by `EIO`: the call reports zero bytes when no earlier replacement was read, although it consumed 1024. The remaining-byte cap still limits the physical read allowance and the adapter fails closed, so this is an evidence/accounting defect rather than a cap bypass.

Minimal fix: carry the partial byte count out of `read_capped` on error and add it to `charged` when building `FailedRead`. Regression: inject a short successful read followed by `EIO`, both with and without an earlier replaced frame; require the complete cumulative count on failure and in `bytes_read()`.

**R3-3 — P2: repeated sticky failures report the original call's bytes again**

Evidence: `FailedRead.bytes` is defined as bytes read **by this call** (`tart/mailbox/error.rs:209`), but the sticky fast path returns `watch.bytes` without performing a read (`tart/mailbox/slots.rs:366`). That field holds the original failing call's bytes (`:372`). `exact_budget_leaves_the_next_frame_unread` explicitly requires the replayed count (`tart/mailbox/tests/slots.rs:332`).

After a 131072-byte failed read, a second `read_slot`/`poll_guest` call on that slot reports another 131072 bytes although it performs no IO. Summing the public per-call evidence therefore reports 262144 bytes for 131072 actually read. The adapter's own sticky guard prevents this double charge in its current path (`tart/mailbox_guest.rs:105`, `:189`), limiting the defect to the exported lower-level read/poll accounting.

Minimal fix: return zero per-call bytes on the sticky fast path; preserve the original failure count separately if diagnostics need it. Update the boundary regression to require the original count once, zero on subsequent sticky calls, unchanged retry counters, and no additional reads.
