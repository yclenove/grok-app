## Must-fix

1. **M1 — High, introduced: restore dispatch validation for targeted messages.** `W/input/ffi/mod.rs:370` now enters the non-foreground branch before calling `State::validate`; it does only `r.check()` and ledger accounting before `native::post` at `:374`. The base revision validated both delivery routes on the native send thread. The caller still validates at `W/input/mod.rs:258`, but then can await `tracker.prepare` at `:270` and queue another native-worker call. A window/child can disappear, change ancestry, or be replaced during that interval. `PostMessageW` at `W/input/ffi/native.rs:93` does not compare the retained generation, root, PID, or class; a recycled valid HWND can receive the message. This affects targeted keys/Unicode as well as pointer messages. UIPI does not detect same-integrity recipient substitution. Restore the native-thread stamp/security/recipient check outside the ledger for this branch, and cover invalidation between the caller's validation and actual posting. The foreground helper tests never exercise this branch.

2. **M2 — High, incomplete correction: final admission does not preserve the validated window contract across the gate wait.** `State::validate` checks the root's generation/process stamp, frame, scale, and minimized state (`W/input/ffi/mod.rs:120`, `:121`, `:124`). `ExpectedIdentity` retains none of the generation/frame/scale/minimized information (`W/input/admission.rs:12`), and `bounded_admit` only checks foreground, child existence/ancestry, child TID/PID, and class (`:97`–`:108`). Constructible case: validate a foreground window at frame A; wait behind another gate holder; the application programmatically moves/resizes that same window to frame B; acquire the gate. Every scalar check succeeds, but the prepared screen coordinates belong to frame A. A button-only packet can click an unrelated surface at those old coordinates. No physical-input event is needed for this case. Same-thread/class HWND reuse also defeats the reduced identity comparison; `HwndStamp` exists specifically because bare handle/PID/class are insufficient (`W/desktop.rs:8`). Retain the required snapshot and use bounded native checks/invalidation after waiting; do not put desktop enumeration or COM back under the mutex. Security and lease freshness need a separate explicit treatment, discussed below.

3. **M3 — High, unresolved acceptance blocker: establish the actual landing pixel before accepting exact equality; repair the measurement design.** `CURSOR_ARRIVAL_TOLERANCE_PX = 0` (`W/input/pointer_settle.rs:45`) removes the explicit one-pixel false acceptance, but the expected pixel is still an algebraic inverse, not a verified Windows mapping (`:48`, `:53`; `W/input/ffi/native.rs:365`). If Windows consistently lands elsewhere for a given normalized coordinate, every such move exhausts the 15ms loop and returns an uncertain error (`W/input/ffi/native.rs:334`, `:371`). Clicks stop before their buttons and drags can stop while held. This is fail-closed availability breakage; it is not evidence that all coordinates on every desktop fail. The new probe cannot yet establish the required result; see the concrete sampling counterexample below. Correct/verify normalization and arrival together, preserve rejection of an unapplied neighboring move, and obtain valid native measurements. Increasing tolerance would restore the original false-arrival defect.

4. **M4 — Medium, inherited broader R4 gap: one session mutex does not enforce ownership of a multi-packet foreground action.** The original independent-host *mutex-name split* is fixed. However, each packet releases the mutex (`W/input/admission.rs:62`, `:69`; `W/input/hook_probe/gate.rs:40`), while a click sends target movement and coordinate-less buttons separately (`W/input/plan.rs:78`, `:80`; `W/input/ffi/native.rs:218`). Two independent hosts targeting the same foreground root can interleave: A moves to P and releases; B moves to Q and releases; A sends its button at Q. All final identity/foreground checks pass. The action serial lock is per `InputBackend`, not shared across hosts (`W/input/mod.rs:61`, `:136`); injected input from B does not become physical activity (`W/input/hooks.rs:81`). Provide cross-host action ownership, or enforce one active injector, while retaining the short probe/packet gate. Holding the present 40ms probe gate across a whole action/await would starve proof renewal. This is not a claim that the new common name fails to serialize its actual critical sections.

5. **M5 — Medium, inherited and NOT FIXED: enforce proof expiry at dispatch and close the stated latch-budget gap.** `PhysicalClock::available` still accepts age equal to 100ms (`W/input/hooks.rs:121`); supervision checks then sleeps 20ms (`W/input/watchdog.rs:66`, `:67`). `bounded_admit` contains no lease/Stop read. The caller's `check_injection` occurs before tracker acknowledgement, native preparation, and the pointer-gate wait (`W/input/mod.rs:265`, `:270`, `:276`). Native probe authorization also checks generation/phase/Stop flags without proof age (`W/input/ffi/safety/probe.rs:338`). Thus the synchronous expiry-at-insertion requirement and approximately 100–120ms polling window identified in r2 remain. Arrange admission against the current proof deadline and supervision against its absolute expiry; distinguish that policy from unavoidable OS scheduling jitter. ADR `:65` acknowledges nonimplementation and does not waive this requirement.

6. **M6 — Medium, introduced coverage regression: select the real kernel tests in CI, and make their name-conflict test safe to run alongside other processes.** `computer-use/crates/gcu-driver-windows/Cargo.toml:13` adds `required-features = ["test-support"]`, but Windows workspace tests/clippy use no such feature (`.github/workflows/computer-use.yml:112`, `:120`). The desktop job builds only `contract` with `test-worker-faults` (`:238`, `:240`); `xtask` has no pointer-test runner (`computer-use/xtask/src/main.rs:31`). Consequently default `cargo test --workspace` skips this integration target; it does **not** fail compilation because its helpers are missing. Add an explicit Windows invocation such as `cargo test --locked -p gcu-driver-windows --features test-support --test pointer_gate`, plus compilation/lint coverage of that target. Before making it a gate, address the process-global test collision below and strengthen the final-admission regressions described in the coverage table.

This removes allocator contention and makes the bounded-work claim more precise; it is not a claim that `GetClassNameW` waits for a hung target's message loop.
- **Finish error diagnostics.** Creation errors are retained, but `error.code()` is an HRESULT representation (`W/input/hook_probe/gate.rs:100`), despite the messages calling it a Win32 code. Distinguish those encodings. `WAIT_FAILED` still becomes generic busy (`:147`–`:154`), and `ReleaseMutex` errors remain discarded (`:81`). ## Session mutex audit

| Concern | Assessment |
|---|---|
| **Squatting / object-type collision** | The fixed name is predictable. Another process in the same session can create a mutex and hold it, or reserve the name with an event. `CreateMutexW` opens an existing accessible mutex; a different object type or denied access fails. Creation failure is cached forever by `CREATED` (`W/input/hook_probe/gate.rs:90`); removing the conflicting object later does not recover that process. Contention/creation failure prevents the body, so these paths are denial of service, not fail-open input or forged proof. Same-user code with suitable access already has broader input capabilities; do not promote this synchronization object into a security boundary. |
| **Tests in parallel** | Every first `serial()` calls a child that creates an **event using the production name** (`WT/pointer_gate.rs:34`, `:91`, `:127`, `:131`). If any host or another test process has the mutex open, `CreateEventW` fails before the intended diagnostic assertion. Conversely, a host creating its gate while that event exists caches permanent failure. `SERIAL` only coordinates threads in one executable; it cannot protect another invocation/shard/application. Even idle open handles retain the name. Isolate the fault test's namespace/session and keep a separate production-name conformance case. Ordinary libtest parallel threads inside this binary are serialized correctly. Separate GitHub-hosted VMs or Windows sessions do not collide merely because their jobs run simultaneously; no claim that Cargo necessarily overlaps test executables is needed for this defect. |
| **`Local\` versus `Global\`** | `Local\` resolves within the caller's Windows session; it is not process-, user-, or desktop-local. Parent/child and independent hosts in that session open the same name. Other logon/RDP sessions have independent input desktops/cursors and separate objects, appropriately. A session-0 service would not coordinate with a session-N worker; such cross-session native routing is outside the admitted path. `Global\` would add unrelated-session contention and ACL exposure, not repair same-session action ownership. Different desktops in one session are over-serialized by this name, not left with separate gates. |
| **ACL / handle inheritance** | `CreateMutexW(None, false, ...)` uses the creator token's default DACL and a **non-inheritable handle** (`W/input/hook_probe/gate.rs:94`). There is no custom descriptor, `SetHandleInformation`, or gate-handle duplication in the reviewed paths. The worker launcher uses piped stdio (`W/worker/process.rs:32`) and opens the named object itself; it does not inherit the host gate handle. Merely enabling process handle inheritance would not make this non-inheritable handle inheritable. If some other code deliberately duplicated/inherited such a handle, it would retain the same object and access rights, not transfer thread ownership or recursion depth; the child still must wait and cannot release the parent's ownership. Extra handles affect object lifetime, not the exclusion rule. |
| **Abandoned ownership** | Accepting `WAIT_ABANDONED` is correct Win32 ownership handling (`W/input/hook_probe/gate.rs:147`, `:148`); the guard stays on the acquiring thread (`:74`). It grants neither permission nor proof. An owner thread's death abandons the mutex even if another process retains a handle. Keeping the parent's handle open before killing the child (`WT/pointer_gate.rs:255`) correctly prevents object destruction/recreation from masquerading as abandonment. This tests ownership recovery, not draining a predecessor's queued input or releasing its held buttons. Those still require ledger/supervisor cleanup; other hosts have no shared ledger recovery protocol. |

The common name also only coordinates participants that use this version's name. A concurrently running older PID-named binary remains outside it. That compatibility boundary should be explicit.

## Bounded admission, identity, and preparation freshness

**The native metadata reads do not synchronously message the target window.** `GetForegroundWindow`, `IsWindow`, `GetAncestor(GA_ROOT)`, `GetWindowThreadProcessId`, and `GetClassNameW` inspect USER/window metadata; a hung target message pump does not turn them into `SendMessage`/`WM_GETTEXT` waits. In particular, `GetClassNameW` should not be confused with querying arbitrary window text. No new full enumeration, COM, process-token query, or tracing call was found in `WinScalar` (`W/input/ffi/mod.rs:87`). The bounded UTF-16 buffer is at `W/input/ffi/native.rs:16`.

That is a useful bounded-work property, not a hard wall-clock guarantee for syscalls, scheduling, or the subsequent Rust allocation. The first `OnceLock` initialization/CreateMutex can also make acquisition take more than its `WaitForSingleObject` duration (`W/input/hook_probe/gate.rs:90`, `:138`); the 40ms parameter bounds the wait call, not the entire cold path. No Windows hung-target timing experiment was run here.

**No intrinsic TID/class-case/child-root false rejection was found for an unchanged live target.** TID/PID are captured directly from the same child already handed to `WinGate`, rather than guessing the root process's TID (`W/input/ffi/mod.rs:136`, `:149`, `:393`). A live HWND's creating thread does not legitimately change. Both class reads use the same `GetClassNameW` helper; a registered window class does not change case between reads. `expected.root` is the top-level `target.window.hwnd`, while ancestry is checked on `target.hwnd`: a normal focused child is not wrongly compared directly to the foreground HWND. A replaced/reparented control or an owned foreground popup can be refused; requiring re-resolution of that changed surface is conservative. Such identity refusals do not justify accepting stale geometry or recycled identities.

**Keyboard semantics:** Key/Unicode events correctly skip the pointer mutex but still use final foreground/scalar admission (`W/input/admission.rs:40`, `:80`). This preserves the foreground requirement already present in the base revision. It does not verify that the exact child remains focused: changing focus between two controls under the same root can leave the retained child valid while `SendInput` goes to another child. That limitation predates this refactor; do not report the new scalar check as exact-focus verification. Targeted keyboard posting has the new M1 regression.

The foreground ordering is now:

```text
request.check -> enumerate/stamp/frame/WinGate/COM validation -> build INPUTs
  -> ledger lock -> context.begin/reserve
    -> pointer gate wait (pointer packets only)
      -> request.check -> foreground -> child/root/TID/PID/class
      -> SendInput -> optional cursor settle
    -> release pointer gate -> timing log
  -> ledger result/rollback -> release ledger
```

Full `WinGate` is not repeated after preparation. That omission is **not, by itself, proof of a privilege bypass**: process session membership and window creator identity are normally stable; a target does not ordinarily elevate in place with the same HWND, and Windows still enforces UIPI. Repeating WTS/token/virtual-desktop COM under the pointer gate would reintroduce N1. But secure/input-desktop state, session interactivity, virtual-desktop membership, frame/scale, and minimized state are not all immutable or equivalent to foreground-HWND equality. No security generation, freshness token, or invalidation mechanism covers them in `ExpectedIdentity`. The refactor must define which state is rechecked with bounded calls and which is continuously revoked. M2 supplies a concrete stale-coordinate failure; M5 supplies the independent proof-expiry gap. I did not reproduce a secure-desktop/UIPI bypass on Windows and do not claim one.

Ledger uncertainty handling remains conservative. Final no-send errors are normalized only before insertion (`W/input/admission.rs:94`, `:114`); `dispatch_packet` restores the prior marker/truncates only new reservations (`W/input/ledger.rs:124`) and reapplies prior uncertainty (`:139`). Partial `SendInput` and settle failures are not normalized away (`W/input/ffi/native.rs:334`, `:405`). `context.begin()` still precedes gate waiting, so concurrent cancellation can over-report uncertainty before insertion; it does not falsely erase an earlier effect.

## Exact-pixel risk and what the live probe can establish

The histogram does collect both requested-position and inverse-position error, desktop metrics, send/read counts, and maximum error (`WT/contract/unsafe_click_probe.rs:250`, `:261`). That is useful raw evidence. It does **not** currently establish zero-error landing on the production path:

1. **The grid misses precisely the quantization boundaries at issue.** The 16-by-13 grid (`:198`) is 208 coordinate pairs but only 16 distinct x values and 13 y values. The existing same-position probe deliberately uses 65536-based integer pixel bins (`W/input/hook_probe.rs:176`), whereas action arrival uses rounded scaling by `extent - 1` and 65535. A local arithmetic counterexample, assuming the existing probe's bin model `floor(norm * extent / 65536)`, is:

   | Origin / extent / requested x | Action normalized x | New inverse prediction | Pixel-bin prediction |
   |---|---:|---:|---:|
   | 0 / 1920 / 1 | 34 | 1 | 0 |
   | 0 / 7680 / 100 | 853 | 100 | 99 |

   Under that model, a 1920-pixel axis has seven differing requested integer positions, yet **none of the new grid's 16 x samples detects one**. All 13 y samples on a 1080-pixel axis also agree between models. Thus an all-zero 1920x1080 grid histogram can coexist with deterministic exact-settle failures at unsampled pixels. This was checked with local Python arithmetic, not native input; it identifies a test-design counterexample, not a measured Windows mapping. Sample near bin boundaries, immediate neighbors of desktop/monitor edges, representative interior pixels, and fractional action coordinates, with repeated trials.

2. **The DPI context differs from production.** The native worker enters PMv2 via `Com::new`/`DpiContext::new` (`W/ffi/mod.rs:57`, `:75`). `landing_histogram` reads `GetSystemMetrics` without setting that context (`WT/contract/unsafe_click_probe.rs:185`), then compares with physical cursor positions. Other external oracles explicitly establish a physical DPI context because the test executable may lack a DPI manifest (`WT/contract/unsafe_desktop.rs:12`). At mixed/scaled DPI, this probe cannot assume the same metrics/coordinate space as the production worker. Establish and report the matching context and monitor topology; distinguish off-monitor gaps/clipping from normalization error.

3. **One read after a sleep cannot separate arrival latency from rounding.** The probe sends, sleeps 15ms, then samples once (`WT/contract/unsafe_click_probe.rs:237`, `:238`, `:246`). A late sample may still belong to the previous move; an eventual zero-error sample says nothing about whether production observed arrival within its deadline under hook/gate load. Record per-move identity/order, samples and elapsed time through the relevant budget, then a later stable landing. Run alone on the disposable desktop or otherwise exclude probe/action/user interference. The measurement calls raw `SendInput`, never the production gate/settle path.

4. **A green test is not a successful measurement.** Every send can fail, or every cursor read can fail, and `landing_histogram` still returns `Ok` (`:239`, `:246`, `:261`); `live_move_landing_probe` only unwraps/prints it (`WT/contract/live.rs:775`). All histogram buckets can then be zero with no usable observations. Require the full intended valid sample count before accepting a dataset and evaluate the actual error distribution explicitly. The `#[ignore]` text is not an assertion. CI's desktop launcher selects specific cases (`computer-use/scripts/smoke-windows.ps1:240`, `:247`), not this new ignored probe.

Exact equality is the right direction for rejecting the supplied unchanged neighbor, provided the destination is correct. Nothing in this review establishes that the normalized input and inverse match Windows on the supported DPI/topology matrix. The source and ADR `:64` explicitly leave that evidence outstanding; their warning is consistent with, not a substitute for, the independent analysis above.
