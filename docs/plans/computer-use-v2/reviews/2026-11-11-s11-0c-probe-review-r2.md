# S11-M2a independent code review, round 2 — 2026-11-11

**Verdict: REWORK. Do not run HEAD 03323ed4 on the shared Mini yet.** The scope reduction is useful, and several round-1 fixes are substantive. Remaining blockers concern VM ownership/absence, enforceable deadlines, and measurement integrity. There are also two straightforward execution regressions: real C1 cannot start its SSH workload, and C2 cannot enter its second attempt.

Reviewed `cu2/s11-0c-probe`, HEAD `03323ed4331afba5aafd578b90c0d10f87f8a6a1`, against previous `64fef747`, after reading the round-1 report first. References below are relative to `computer-use/`; `src/` means `tools/s11-mailbox-probe/src/`. Basis: ADR 0019 §3 and §5, and the clone/inventory rules in `scripts/s11-0-probe.sh`. This was a static review: no network, Cargo, probe execution, test execution, source changes, or commit. Mutation statements below are predictions from test inspection, not executed mutations.

The accepted scope is **C1/C2/C8 using an ordinary host-private export**. Round-1 findings **#1, #4, and #13 are deferred to M2c**, not blockers in this review. There is no real hdiutil/diskutil/detach path left. Nothing here requires the production supervisor, production leases, admission, or the deferred volume experiments.

## Numbered findings

1. **must-fix — Unresolved clone creation becomes confirmed absence; ownership remains only a boolean/name.** `src/host.rs:185`, `:214`, `:224`, `:402`, `:451`; `src/clone.rs:87`, `:127`. Round-1 #6, with a new false-absence regression.

   **Failure scenario:** `tart clone` times out, overflows, or returns zero but its subsequent list cannot be trusted. `decide_after_clone` correctly returns `Ambiguous`, and the driver correctly refuses to adopt/delete that destination. But `owned` remains false; teardown initializes `vm_absent = !owned`, and returns true after scratch cleanup without independently proving the name absent. The report says `cleanup_absent: true`. The existing test at `host.rs:819`–`:821` explicitly expects that incorrect result. A destination left by an uncertain clone is neither owned nor absent. The outer subcase loop consequently has no quarantine barrier against subsequent attempts.

   Separately, a successfully created clone is never bound to a recorded clone directory/config incarnation. Replacing the destination at the same name after the successful list makes later `stop`/`delete` act on the replacement. Random naming prevents accidental initial collision; it does not detect replacement after ownership was established.

   **Minimal fix:** use a small explicit state: not dispatched, positively absent, owned incarnation, or unresolved. Unresolved creation must preserve resources, report quarantine/absence unknown, and stop later attempts, with zero stop/delete dispatch against the ambiguous name. Persist the small identifying receipt needed for manual recovery. For an owned clone, bind the actual local clone directory/config identity and revalidate before start/stop/delete. Because Tart effects use names, also require a controller-held exclusion window against concurrent changes to that exact clone path/name through cleanup; polling alone does not close check-to-effect replacement. This can be a lab precondition, not a new production identity framework. Continue to require clone exit zero plus a complete successful inventory before ownership.

2. **must-fix — There is no independent bound on filesystem work, and the phase deadlines are incomplete.** `src/host.rs:225`, `:358`, `:396`, `:425`, `:448`; `src/budget.rs:79`, `:89`; `src/cases.rs:244`, `:398`; `src/publish.rs:50`, `:56`, `:69`, `:78`; `src/identity.rs:153`. Round-1 #8 remains open; this is decision (a).

   **Failure scenario:** guest `open`, metadata, read, rename, or fsync blocks on virtiofs. It runs in the guest control thread without a guest-local workload deadline. The host's corresponding filesystem calls, local scratch IO, and final report IO also run directly in its orchestration thread. No timer can stop that same blocked thread. Killing the local SSH client does not establish remote termination. There is no watchdog outside this boundary that will stop the owned VM and end the run. A supervised terminal and manual instructions cannot enforce the stated no-indefinite-hang bar.

   Even when syscalls return, `drive_c1` takes no attempt/load deadline: every frame and summary creates a fresh three-second visibility end. Teardown has no `min(first_cleanup + 60s, attempt_end)` deadline. If stop fails early, `runner.finish` can wait until the Tart child's original approximately 240-second end, using far more than a 60-second cleanup phase. `identity::cleanup` checks no deadline between deletions, so it can dispatch another unlink after the one check at `host.rs:448` has become stale. `call_list` can also borrow cleanup time through its unconditional experiment-to-cleanup fallback, without an explicit phase transition.

   **Minimal fix:** add a minimal independent outer watchdog/process boundary, retaining VM control outside the process doing potentially blocked filesystem IO. Give each subcase one attempt end, one load end of at most 60 seconds, and a cleanup end of at most 60 seconds from its first cleanup action, all clamped to the attempt end. Pass the existing absolute end, not a renewable duration, to commands, polls and each effect. Give the guest a local load bound as well. On expiry, stop new effects, terminate/reap within the reserved interval, and stop the positively identified own VM; if worker/tree termination cannot be proved, retain the export, mark quarantine and do not continue or delete. The watchdog itself must not wait on the blocked worker, its pipes, or mailbox FS calls. A controller wrapper is sufficient if it implements this boundary and is part of the reviewed run command; no general supervisor framework is necessary.

3. **must-fix — FD-based IO is substantially better, but the expected mailbox parent identities are still not enforced.** `src/host.rs:189`; `src/cases.rs:295`, `:398`, `:690`, `:951`; `src/publish.rs:42`, `:58`, `:69`; `src/slot.rs:44`, `:74`. Round-1 #3 is only partially fixed.

   **Failure scenario:** after creation, replace `guest-write` or `host-write` with another ordinary 0700 directory on the same filesystem. The creation identities exist in `Tree`, but the workload does not receive/compare them. `open_sub` simply calls `verify_private_leaf` again and adopts the replacement. An ordinary host-private export makes same-device/FSID replacement especially easy to overlook: those checks can all pass on a different directory. After opening, the directory FDs remain usable even if their names are moved, and there is no before/after comparison of the recorded directory chain. Successful data exchange can then describe a displaced/replacement mailbox rather than the declared export.

   `publish` now retains the source FD across `renameat`, checks the last destination inode, and propagates directory-sync errors: keep those improvements. It still does not compare source identity before versus after write/fsync and after rename, or revalidate the recorded target directory. `read_slot` checks file metadata before/after but never checks that the final name still identifies that FD. It also converts every read error into `Size`, so EIO can be misreported as a torn/integrity failure rather than IO unknown. No bounded whitelist inspection of the mailbox or retained subdirectories occurs; `Tree::cleanup` skips all retained directories entirely. Unexpected guest entries therefore evade both the workload and cleanup checks.

   **Minimal fix:** pass the original recorded directory identities into the workload, open from the trusted export parent using no-follow FDs, and compare the expected parent chain before/after IO. Keep the publication source FD and original identity through source-name/moved-object verification. For reads, add the final same-parent name-to-FD check alongside dev/FSID/nlink/size/timestamps, and distinguish actual IO errors from size overflow. Add a small per-case entry whitelist with a whitelist-size-plus-one enumeration cap; do not traverse guest directories recursively. Expected synthetic frames can remain as intentional retained evidence. Unexpected names/types or directory replacement must remain an integrity error/quarantine, not a new adopted baseline. Retention must not imply validation.

4. **must-fix — C1 can still erase an observed mutation and report incomplete timing or failed execution as success.** `src/slot.rs:72`, `:75`; `src/cases.rs:261`, `:315`, `:442`, `:477`; `src/publish.rs:77`, `:120`; `src/host.rs:368`. Round-1 #11 remains partially open.

   **Failure scenarios:**

   - An in-place rewrite changes mtime/ctime/size while the FD is being read. `read_slot` returns `Replaced` before classifying the captured bytes, and `wait_frame` retries **every** `Replaced` as if it were merely an old inode unlinked by a legitimate rename. A mixed read followed by a valid read can disappear again. The comment about old `nlink == 0` does not justify treating all metadata changes as that case.
   - A directory fsync or publication verification stalls for 150 ms while open/write/file-fsync/rename are individually fast. `sum_pub` adds only those four timers, omitting both directory fsyncs and verification. The reported publication slice can stay below 100 ms despite the actual call exceeding it. Old/absent/replaced polling IO is discarded from the maxima, and `guest_read_us` measures the entire wait interval rather than the actual timed read operation. These categories are still inconsistent between directions.
   - The guest publishes a valid summary, then its final directory sync fails. SSH exits nonzero. The host has enough frame/summary bytes to judge `ok` and ignores the SSH status, timeout, overflow and IO-error flags unless `reap_unknown` is true. Transport bytes must not be measurement evidence, but successful bounded execution is still a prerequisite for declaring the workload complete.

   **Minimal fix:** distinguish the narrowly justified old-unlinked-frame retry from in-place mutation/other replacement; preserve integrity evidence or an explicit unstable-read unknown across retries. Time the entire publication call and retain the per-operation maxima, including sync/verification and unsuccessful polling IO. Use explicit visibility-wait versus read-IO labels. Require bounded SSH completion with status zero and trusted execution flags for C1 completion; retain any already-observed integrity failure even if execution later becomes unknown. Do not erase partial counts/errors on an early return. The now-required guest summary, full field parsing, digest comparison and immediate malformed-frame failure are good fixes and should remain.

5. **must-fix — C2's file-sync evidence crosses the boundary being tested, and the third frame is not validated.** `src/cases.rs:577`, `:595`, `:632`, `:662`, `:739`, `:768`, `:819`. Round-1 #12 remains partially open.

   **Failure scenario:** the file-sync case writes/fsyncs `c2-part`, then calls `write_progress` in the **same mailbox directory** with `sync_dirs = true`. That routine renames the progress record and fsyncs that parent twice. The purported file-sync-only cut has therefore included a successful parent-directory sync before fault exit. This changes the experiment even though `dir_synced` is reported false. The dir-sync case also adds progress publication/sync work after its claimed exit boundary. The intentional exit code 86 proves the program reached its final return, not that it exited immediately at the advertised syscall boundary.

   Independently, `read_c2` sets `part = true` for **any** readable capped ordinary file. An empty file, a truncated write, or seq 1 bytes in `c2-part` can produce `not-ack` for file-sync. `samples` is copied from the guest's self-reported `completed` counter; the host reads only the final frame, not two/three independently observed visible samples. `parse_progress` does not require `v == 1`, and missing `errno` or arbitrary integer `dir_synced` values can pass non-dir-sync rows. Thus the test's claimed complete old/new bytes and exact progress schema are weaker than stated.

   **Minimal fix:** make progress instrumentation leave the data-directory sync state unchanged at each cut. For example, use a separate fixed evidence subdirectory for the completion record, with no sync of the tested parent after the file-sync/rename cut; any further measurement effects must be explicitly part of the protocol. Verify `c2-part` is exactly the expected complete seq-3 frame and validate every progress field/version with closed values. Report planned/attempted publishes, completed renames, validated surviving frames and third-publish phase separately. Preserve the already-improved status-86 gate and unknown classification for arbitrary guest failure; never invent per-sample host observations from a final counter. No result here proves power-loss durability.

6. **must-fix — C2 attempts reuse a retained path, and omitted subcases can fold into success.** `src/host.rs:123`, `:132`, `:137`, `:185`, `:189`; `src/cases.rs:107`, `:118`. New in the rework.

   **Failure scenario:** all C2 subcases receive the same `attempt` and share identifiers. `run_sub` constructs the same clone/base name every time; the base is deliberately retained. After a completed file-sync subcase, the next `mkdir_0700_at` returns EEXIST. This error occurs before the `built` closure and escapes through `run_case`'s `?`, so the driver produces no final `report.json`, discarding the first row and explicit records for the remaining rows. Reusing the mailbox instead would contaminate subsequent measurements with prior frames and progress records.

   After fixing that collision, another path remains: if the experiment budget expires between subcases, later rows become `not_run`. `fold_verdicts` removes those rows before evaluating completeness and deliberately reports `not-ack` for `[not-ack, not_run]` (`cases.rs:1088`). That can exit zero despite missing required fault-boundary coverage. The same rule accepts `[ok, not_run]` as `ok`.

   **Minimal fix:** allocate a fresh random attempt/clone/export/share per subcase; preserve any aggregate run deadline in addition to the per-attempt ends. Catch setup failures into a row and always finalize the report. Require all planned rows for a completed aggregate: omitted required rows mean incomplete/unknown, with observed failure and quarantine retaining their precedence. Do not change counts or erase old data to make a reused attempt look fresh.

7. **must-fix — Deployment is fresh and fail-closed, but its private executable boundary is still assumed.** `src/dispatcher.rs:15`, `:23`, `:29`, `:182`, `:194`, `:204`; `src/host.rs:259`; `src/main.rs:120`. Round-1 #10 is partially fixed.

   **Failure scenario:** `/Users/eval` or its deployment child has an unexpected write ACL/owner, or `.ssh/authorized_keys` is an existing hardlink/special file. The initializer checks final symlink/existence conditions and creates a 0700 child, but verifies neither the parent trust chain nor effective inherited ACL grants, owner, regular-file type and nlink. An untrusted second principal can replace the executable tree under an untrusted writable parent, and the initializer can append/chmod through an unexpected existing authorized_keys object. Later verify/run arms do not validate the deployment directory or its metadata. A digest comparison on such a mutable path cannot protect the digest-to-exec interval. `/bin/sh` and `/usr/bin/shasum` are absolute paths, but their approved identities are not established/recorded by this driver.

   The dispatcher digest and probe digest now verify upload integrity; keep that. However, the host derives the probe digest from whatever `current_exe` it reads and has no reviewed-artifact digest/size comparison or receipt. Self-consistent copy verification is not the controller's fixed-artifact approval check.

   **Minimal fix:** validate the fixed guest home/deployment chain, owner/mode/ACL and relevant file type/nlink before installation/activation, retaining protection until execution ends. Fail closed on unexpected `.ssh`/authorized_keys objects; do not broaden privileges or rewrite their trust policy to force installation. Pin interpreter/dependency identity through the approved golden receipt or explicit fixed checks. Compare the host artifact's capped size/digest to the controller-approved artifact and record that binding before upload. A short fixed initializer plus the existing literal dispatcher is sufficient; retain exact command matching and publickey-only/no-forwarding SSH. No shell-injection path through `SSH_ORIGINAL_COMMAND` was found in the current literal dispatch arms.

8. **must-fix — Runner error paths can lose child ownership and turn unverified termination into a clean result.** `src/proc.rs:47`, `:95`, `:106`, `:233`, `:261`, `:286`; `src/host.rs:416`, `:425`. Remaining round-1 #6/#7 edges; the old unbounded waits/joins themselves are removed.

   **Failure scenarios:** after `command.spawn` succeeds, failure taking/configuring either output pipe returns an error and drops `Child` without a bounded terminate/reap guard. Rust dropping `Child` does not kill it. Separately, `reap_past` observes an already-exited direct child, discards `pump`'s overflow/IO-error results, and returns an apparently untimed-out clean exit without handling its descendants. Normal finish sends group SIGKILL but discards the result and never establishes group/tree absence; `reap_unknown = false` proves only the direct child was reaped. Teardown treats that flag plus one `stopped` inventory as sufficient for delete. A surviving Tart/Softnet descendant is not represented by those observations.

   **Minimal fix:** own each successfully spawned child immediately, with cleanup on every later setup error. Use one bounded completion/termination path; propagate all drain flags, classify late/unproved completion as unknown, and retain an explicit unresolved-tree outcome when group cleanup or independent Tart/Softnet exit cannot be established. Do not dispatch delete after that outcome. Preserve the finite nonblocking drain and `try_wait` approach; no blocking `wait`, pipe-thread `join`, or deadline restart should return. Harmless runner tests must inspect descendant survival and delayed `finish`, not just elapsed time and the parent's exit status.

9. **must-fix — Report publication errors are silently discarded.** `src/host.rs:160`, `:163`, `:164`, `:165`; `tools/s11-mailbox-probe/README.md:28`. New evidence-delivery defect in the rework.

   **Failure scenario:** private-root revalidation, exclusive report creation, or a partial write fails (for example EIO/ENOSPC). `finish` still returns `RunOutcome` with the measured verdict, and `main` can exit zero. The documented sole authoritative artifact is absent or truncated. A controller cannot distinguish that result from a fully published report by the exit status.

   **Minimal fix:** propagate report IO failures and make a complete bounded report publication a prerequisite for success. Write through the verified output FD, check the complete write and required sync/publication results, and use a fixed exclusive temporary record plus atomic publication if appropriate. On failure retain resources/evidence and return nonzero with an explicit report-publication failure. Preserve measurement failure/quarantine separately from the operational error. Avoid reparsing the just-generated JSON as a substitute for handling IO results.

10. **should-fix — Real C1 always returns `busy` before starting the guest workload.** `src/proc.rs:27`, `:338`; `src/host.rs:236`, `:367`; `src/runner.rs:225`. New execution regression.

    **Failure scenario:** the sole `ProcessRunner.live` slot already holds the Tart run child. C1 requests a second persistent spawn for SSH, which unconditionally returns `busy`. Local C1 thread tests bypass this path, and `Fake` supports multiple spawned records, so they do not reveal it. This currently returns an honest unknown; it is not itself a silent atomicity pass, which is why it is should-fix under this round's restricted severity bar.

    **Minimal fix:** give the two fixed roles, Tart and workload SSH, distinct owned handles/runners. Both need their original ends and guaranteed cleanup on every exit. A two-role implementation is enough; do not build a generic process registry. Exercise the host orchestration with the same two-spawn restriction as the real runner.

## Grok NEEDS-DECISION recommendations

| Item | Recommendation |

| **(a) blocking FS calls in the control thread** | **Require a minimal outer watchdog.** Manual recovery plus a watching human is useful fallback documentation, not the enforcement required by the task's no-indefinite-hang bar. A reviewed controller wrapper owning the exact VM and an absolute end is acceptable. It must survive a stuck IO worker, avoid blocking reap/FS calls itself, stop only the positively identified own VM, quarantine uncertain effects, and stop subsequent attempts. See finding 2. |
| **(b) expected guest frames retained** | **Whitelist by case and retain as evidence.** Do not delete guest-created objects merely because their names look expected. C1: known root result/temp names and the two fixed directional frame/temp names; C2: frame/part/progress/temp names plus absence of an ACK result; C8: fixed result/temp names. Current blanket skipping of retained directories is insufficient. Name the retained artifact state separately from VM/scratch absence. |
| **(c) file-sync samples two versus ADR three publishes** | **Keep two completed renames and a third attempted publish stopped after file fsync.** Do not invent a third completed/visible sample or rename it just to satisfy the count. | **(d) exit zero for not-ack** | **Accept as experiment-completion status**, with report verdict `not-ack`, never `ok` or an ACK/durability claim. | **(e) C8 with at least two principals only mapping-not-measured** | **Accept honest deferral in M2a.** Do not add accounts, su/sudo or credentials. ## Focus of the final review

Round 3 should inspect the reduced implementation and the actual watchdog/controller command, with focused evidence for: ambiguous clone preserving resources and stopping later work; replacement clone/directory refusal; two simultaneous child roles; all three fresh C2 attempts; skipped required rows failing completeness; file-sync instrumentation not syncing the data parent; malformed part bytes rejected; C1 mutation followed by valid bytes never recovering to ok; slow directory sync/old-read IO reflected in timings; delayed finish and setup failure preserving child/tree uncertainty; and report IO failure preventing success. These are targeted boundary checks, not a demand for another broad fake framework or production transport implementation.

Real Mini behavior, including native ACL/FSID compatibility and virtiofs timings, remains **not_run in this review**. The owner DEFAULT-network notice remains a prerequisite for a later corrected live run. A successful M2a report would establish only its explicitly observed ordinary-directory mailbox mechanics; deferred volume, production liveness/isolation and C8 mapping claims remain unproved.
