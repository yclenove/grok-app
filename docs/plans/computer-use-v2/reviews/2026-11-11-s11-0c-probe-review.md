# S11-M2a independent code review — 2026-11-11

**Verdict: REWORK. Do not run this revision on the shared Mini.** The implementation has useful conservative checks, but it does not yet meet the stated bar for destructive identity, bounded execution, or measurement honesty. This requires changes to the resource/command boundaries, not merely approval of the eight decision items.

Reviewed branch `cu2/s11-0c-probe`, HEAD `64fef747dc2e640c7158acff32211744dfea2e78`. All source references below are relative to `computer-use/`; `src/` abbreviates `tools/s11-mailbox-probe/src/`. Compared against ADR 0019 §§2/3/5, ADR 0018 §§13/14, and `scripts/s11-0-probe.sh`. This is an independent static review: no network, Cargo, probe execution, code edits, or commits. The source contains 28 test attributes; the reported Mac/Linux passes were not rerun or treated as real-path evidence.

This review does not require M2a to implement the production supervisor, leases, admission, or block-all transport. It does require the lab probe's own mutations, deadlines, deployment, and observations to be safe and accurately described.

**Findings, ordered by impact**

1. **must-fix — Detach checks do not bind the destructive effect to the attachment.** `src/host.rs:1109`, `src/host.rs:1131`, `src/host.rs:1152`; `src/identity.rs:31`.

   Principle: ADR 0019 destructive rule 1 explicitly rejects “just checked `/dev/diskN`” as effect-time identity. Normal and force detach each require the exclusive host window or a measured operation that preserves attachment identity through the effect.

   Failure scenario: the probe checks its image on `/dev/disk4`; another host job detaches it and attaches an unrelated image that reuses disk4 before `hdiutil detach /dev/disk4` runs. The command detaches the unrelated image. Repeating the readback before force has the same race. There is no exclusive-window precondition/receipt in the CLI or README. The predicate also does not receive the current image inode or parent identity, does not compare the recorded slice with the current slice, and accepts a missing current mount when other values happen to match (`identity.rs:63`).

   Minimal fix: require and record the ADR's actual exclusive window for disk and target-path changes before permitting any destructive command; otherwise quarantine without dispatch. Revalidate the complete original image/parent, whole-device/slice/all-mount, UUID and mounted-root identity before **each** normal/force effect, under that window. Do not claim that extra polling or a probe-only lock solves device reuse. Force remains once only, with time reserved for readback and cleanup.

2. **must-fix — The private-root verifier accepts attacker-controlled ancestors.** `src/volume.rs:51`, especially `:72` and `:82`; `src/main.rs:136`; `src/osutil.rs:237`.

   Principle: a private leaf protects contents only while its entire path is anchored through trusted directories. The proposed StrictModes-like policy is reasonable; the implemented policy is materially weaker.

   Failure scenario: put the 0700 leaf below a directory owned by another non-root user with mode 0755, or a group-writable ancestor without other-write. The verifier accepts the first different owner, checks only the other-write bit, then returns without examining higher ancestors. That owner/group can rename the containing directory and install a replacement or symlink between a later identity check and pathname cleanup. The probe can then unlink or chmod an unrelated target under its own authority. A symlink above the first different owner is also never inspected. Checking the leaf after creating/chmodding it is too late to authorize those initial effects.

   Minimal fix: anchor from a trusted root using directory FDs and no-follow component opens; walk **every** component. Require the leaf to be current-UID/0700 and every ancestor to be current-UID or root, with no group/other write and no effective ACL write grant. Reject dot/dot-dot and non-normal components. Reject sticky exceptions unless separately justified in the approved policy; they are not the policy proposed in decision #2. Create with 0700/0600 at creation under umask 077, and use FD-based chmod. Check that execution is non-root. Do not rely on a final-path `lstat` to detect intermediate symlinks.

3. **must-fix — Publication and reads lose the recorded directory/volume boundary.** `src/publish.rs:40`, `:55`, `:59`; `src/slot.rs:39`, `:64`, `:108`, `:130`; `src/osutil.rs:212`.

   Principle: fixed ASCII leaf names do not make their parent path trustworthy. ADR §3 requires anchored parent FDs, recorded directory identities, the retained publication source FD, and expected dev **and** FSID.

   Failure scenario: a guest replaces `host-write` with a directory or a symlink such as `../host-stage`. Publication closes its source FD, then performs pathname `rename`, following the substituted destination parent and operating outside the export. Readback may reject the symlink only after the rename. Under an intact dedicated HFSX mount, a rename to an APFS host file normally fails with EXDEV; that is a useful limit, but it is not an implemented identity check. Parent/mount replacement also makes that filesystem assumption unsafe. Independently, a replacement ordinary `guest-write` directory is accepted because no recorded parent identity is compared. Its files' `st_dev` is checked against that newly opened directory, not against the recorded volume, so this is a circular binding.

   Minimal fix: walk from the verified mounted-root FD through no-follow directory opens and compare each recorded identity before/after IO. Keep the source FD through `renameat` between verified stage/target FDs; verify source type/nlink/dev/FSID and destination absent-or-last-slot identity. Check both directory sync results; they are currently discarded. Reads must check expected mounted-volume dev/FSID, directory identity, and file mtime/ctime as well as the existing inode/nlink/size checks, then verify the name through the same parent. Bound unexpected-directory-entry inspection per §3. Preserve the rule that guest content is never recursively traversed or cleaned.

4. **must-fix — The durable ledger cannot establish cleanup ownership, and attach can adopt a replacement image.** `src/ledger.rs:12`, `:150`; `src/host.rs:502`, `:614`, `:618`, `:1244`, `:1326`, `:1338`.

   Principle: record the original parent/child identity before continuing, and never substitute a later object's identity for the one this run created. Every destructive step needs its own durable intent and identity authorization.

   Failure scenario: replace I after create but before attach readback. The attach record takes a new `lstat(I)` at line 614 without comparing `image_id`, and later unlink authorizes that adopted inode. The replacement was not created by this run. Separately, a crash loses the complete attachment binding: the ledger has only logical names and dev/ino events, no parent relationships, UUID/FSID/device mapping, clone incarnation/config, or mounted child identities. `mount_underlying` is actually sampled **after** attach, so it describes V, not M₀; the original M₀ survives only as another in-memory Node. Cleanup uses pathname remove operations and logs no individual seed/SSH rmdir/unlink intentions. Failed stats are collapsed to absence (`host.rs:1035`, `:1201`, `:1227`, `:1339`), although EACCES/EIO is not ENOENT.

   Minimal fix: persist original parent/child metadata and the complete attachment/clone binding, with distinct M₀ and V records, before boot or further effects. Compare the image to its create record before attach and destruction. Use verified parent FDs and no-follow child checks for each unlink/rmdir, within the exclusive window from finding 1; record intent/effect per step. Only explicit ENOENT is absent. On missing identity, lost create/attach reply, failed stat, or ledger failure, preserve the resource and quarantine. Sync the directory containing a newly created ledger before depending on its durability. Recovery may remain manual for this lab tool, but the retained record must make safe identification possible; a new `--out` is not recovery proof.

5. **must-fix — Incomplete command/schema readback can become authoritative absence.** `src/plist.rs:43`, `:372`; `src/host.rs:982`, `:1218`; compare `scripts/s11-0-probe.sh:245`.

   Principle: unknown is not absent, and parseable stdout from an unsuccessful query is not a trusted inventory.

   Failure scenario: `hdiutil info -plist` exits zero with an unexpected valid plist, such as `<dict/>` or an `images` value of the wrong type. `attached_images` returns an empty vector, authorizing `unlink_unattached` despite a possible live attachment. It also silently skips empty entries and collapses multiple slices/mounts to the last one, losing the “all attachments/all mounts” requirement. Separately, `list_vms` never checks `out.status == 0`; a failed Tart query containing a valid `[]` can authorize VM absence. The verified shell probe explicitly rejects nonzero list status before parsing.

   Minimal fix: give attach and info distinct typed schemas. Require the expected top-level dictionary and `images` array for info, and require every entry's identity fields; only an explicitly present, correctly typed empty array proves an empty inventory. Reject duplicate/ambiguous mappings and unrepresented extra slices/mounts. Require successful exit plus complete capped output for all authoritative queries, including Tart list. Bind any accepted image-path spelling to the original image identity rather than treating an unrecognized alias as absence. Test wrong-type/missing arrays and nonzero commands with otherwise valid stdout.

6. **must-fix — VM ownership and stop barriers are weaker than the claimed cleanup proof.** `src/clone.rs:79`, `:119`; `src/host.rs:833`, `:917`, `:997`, `:1059`.

   Principle: clone success plus exact-name presence is a necessary baseline, but a remembered boolean/name is not an incarnation check. VM/Tart/Softnet exit must be proved before volume teardown.

   Failure scenario: the original clone is removed and another VM is installed at the same name before cleanup. `owned = true` is retained, and the probe stops/deletes that replacement. Before detach, `settle_vm` discards both stop and `runner.finish` outcomes; a `stopped` list entry is allowed to substitute for confirmed child/tree exit. A timeout/reap failure can therefore be followed by delete/detach. C1/C2/C8 also discard the SSH child's terminal status, losing whether the guest completed or was killed. If the ledger effect write fails immediately after spawn, the child handle has not yet been stored, so later teardown cannot finish it.

   Minimal fix: bind and persist a host-observed clone directory/config/incarnation and compare before start, stop and delete, under the path exclusion window. Preserve the verified shell probe's no-adoption rule for failed/timed-out/overflowing clone. Store each spawned handle immediately, before another fallible operation. Consume and propagate finish/stop results and independently confirm the exact Tart/Softnet tree has exited; uncertainty means no detach/unlink and no next attempt. Record the intended C2 fault exit separately from an arbitrary SSH error. No production admission claim is required here.

7. **must-fix — The real subprocess runner can hang forever after its apparent deadline.** `src/proc.rs:89`, `:133`, `:181`, `:213`, `:256`.

   Principle: the cap includes termination, reaping, stdin delivery and output collection; a deadline on `try_wait` alone is insufficient.

   Failure scenarios: (a) hdiutil is stuck in uninterruptible IO: after SIGKILL, `child.wait()` at line 146 has no deadline. (b) a child exits while a descendant retains stdout/stderr, or retains stdin without consuming it: the unconditional reader/writer thread joins wait forever. This happens even on a nominally successful parent exit, because surviving descendants are never closed out. (c) a command floods output: buffers stop growing, but overflow is never observed by the wait loop, so the process continues until its full timeout. Read/write errors and drain-thread panic can also be converted into shortened/default output without marking it untrusted. `terminate` returns as soon as the direct child exits after TERM and can leave its descendants alive without ever sending KILL to the remaining group.

   Minimal fix: use one absolute command end with reserved kill/reap time and bounded pipe IO, including descendants retaining pipes. Stop dispatch and mark `reap_unknown` if exit cannot be established by the deadline; never block on wait/join or interpret missing output as success. Observe overflow during execution and terminate immediately. Preserve read/write errors. Keep process-group ownership valid until group handling is finished. Bounded harmless helper-process tests must exercise these real runner paths; scripted `Runner` success cannot establish this property. Do not restore `ulimit -f`, which the Mini-verified shell probe already showed can kill legitimate Tart operations.

8. **must-fix — Per-command durations are repeatedly reset; load/teardown and filesystem operations have no hard bound.** `src/host.rs:445`, `:820`, `:962`, `:997`, `:1003`, `:1028`; `src/proc.rs:54`, `:97`; `src/cases.rs:346`; `src/publish.rs:45`; `src/ledger.rs:107`.

   Principle: sub-budget maxima share an absolute stage/attempt end and include kill/reap. Measuring overrun afterward is not enforcing a deadline.

   Failure scenario: three 60-second SSH setup commands follow clone and six IP queries with fresh budgets. The spawned Tart and SSH commands store no start/deadline at all; their argv timeout is discarded by `spawn`, and `finish` starts another full wait later. Teardown can spend 60 seconds finishing SSH, 20 stopping Tart, another 20 finishing Tart, then multiple 5-second inventory/delete/detach queries before it checks elapsed time. It can still dispatch destructive effects after the 60-second teardown budget has expired. The final mount query is outside even that post-hoc check. Separately, a stuck HFSX/virtiofs `open/read/fsync/rename/unlink` or ledger sync blocks the controller thread indefinitely; O_NONBLOCK on a file does not bound these syscalls. The 3-second visibility timer is checked only after the blocking read returns and does not enforce a 60-second guest load deadline.

   Minimal fix: establish preparation/start-volume/load/cleanup and command absolute ends once, passing the minimum remaining budget before every IO/effect. Reserve termination/readback time inside those ends. Store a spawn's original end; never restart it on finish. After expiry, stop new destructive dispatch and quarantine. Put potentially blocking filesystem work behind a bounded process boundary supervised by the controller; on unconfirmed termination preserve resources, mark unknown and stop subsequent attempts. Do not attempt to fix a blocked syscall by another timer in the same blocked thread. This is a lab boundedness requirement, not a demand to implement M4's production lease loop.

9. **must-fix — First keyscan is trusted without proving which clone answered.** `src/host.rs:841`, `:853`, `:862`; `src/sshdriver.rs:94`, `:130`.

   Principle: `StrictHostKeyChecking=yes` pins subsequent connections to the scanned key; it does not authenticate the initial key or bind an IP to a clone/boot. The ADR checklist expressly disallows automatic key acceptance.

   Failure scenario: stale DHCP/IP information, another eval VM, or an impersonating endpoint answers the first scan. The probe pins it and uses the general eval key to install its dispatcher there. Another VM made from the same golden may accept that key, so this mutates a VM not created by the run. Public-key authentication does not disclose the private key, but neither does it prove server identity. There is no independently verified clone/IP/boot binding in this flow.

   Minimal fix: compare the offered host key to an independently trusted image/clone manifest or an authenticated host-side source and verify the exact clone/IP/boot association before **any** install. Stop on ambiguity. If the controller wants a TOFU exception for a demonstrably exclusive, trusted lab clone, record that as a specific ADR exception with its assumptions; the current automatic first-keyscan flow cannot be called checklist compliant. “Just created a clone” alone is insufficient.

10. **must-fix — Bootstrap/deployment does not establish the new private executable boundary.** `src/sshdriver.rs:53`, `:62`, `:160`; `src/dispatcher.rs:41`, `:58`, `:78`; `src/host.rs:779`.

    Principle: a bounded, constant initializer using the existing eval key is an acceptable minimal lab bootstrap **after** authenticating the own clone, but it must create and verify the restricted environment before claiming success.

    Failure scenario: `/Users/eval/.s11-0c` already exists with unexpected owner/mode or writable contents. `mkdir -p` reuses it; the installer neither validates those properties nor runs with `set -e`, and overwrites dispatcher/share/subcase entries. A failed install operation can still end in `exit 0`. Token redirections can follow existing links. The dispatcher checks some final symlink/file properties but not owner/mode/nlink/parent replacement; its verification stamp can be truncated through an existing link. The script itself is not checked for complete copy/digest before being installed. Hashing the uploaded probe and rehashing immediately before exec are good, but cannot protect a writable directory or bind hash-to-exec against a replacement race. Remote lifetime is also not bounded merely by killing the local SSH client.

    Minimal fix: use a fresh exclusive private deployment directory outside the mailbox, rejecting preexisting paths; verify parent/owner/mode/ACL/file type/nlink and retain that protection through execution. Fail every initializer step closed. Verify the complete dispatcher and probe copies against the controller's approved artifact sizes/digests before activation; pin the interpreter/dependencies and record those identities. Apply guest-local workload deadlines and stop the own VM if remote termination cannot be established. Give the fixed initializer its own constructor instead of the generic “anything starting with `umask 077\n`” bypass in `ssh_cmd`. Keep publickey-only/no-forwarding options and forced-command restrictions; do not open SFTP or a general shell fallback.

11. **must-fix — C1 can hide tearing, succeed without the guest summary, and report invented timing categories.** `src/cases.rs:98`, `:124`, `:346`, `:396`, `:565`; `src/host.rs:930`.

    Principle: any observed mixed frame fails atomicity; unavailable evidence stays unknown; each reported timing must correspond to the operation actually timed.

    Failure scenarios:

    - `wait_frame` observes non-spec bytes and sets `mixed = true`, then sees the expected frame and returns `torn = false` at line 355. A real transient tear disappears from both host and guest observations. A prior wrong-filesystem observation can be erased similarly. Malformed-size observations are treated like retryable absence rather than classified integrity evidence.
    - After the last guest frame arrives, the host reads the result slot just once. The guest may still be writing it. Missing/invalid slot becomes `None`; `judge_c1` can nevertheless return `ok` for 16 samples. `parse_c1_slot` does not require/type-check torn/lost/max fields, and the caller discards even the returned sample count. The guest's timings and errors never enter the report.
    - Host write time is labeled both open and read time; host read time is labeled guest publish time. Stage/parent open time, directory fsyncs, readback and failed/old polling reads are outside the reported maxima. A one-second open or directory fsync can therefore be omitted from the 100 ms observation. `slice-over-100ms` is just a note and does not prevent an `ok` verdict.

    Minimal fix: make integrity violations sticky and distinguish a complete permitted old frame from mixed/invalid evidence. Obtain the final same-volume summary through bounded mailbox polling; require all fields, eight guest samples, zero tears/losses and the matching digest before success. Preserve guest-local measurements and time actual open/read/write/fsync/rename/full-publication slices, including failed observations. Missing measurements are null/unknown, not reused numbers. Apply the documented latency and scheduling gates; report small-sample maxima without p99 claims. Ordinary IO/watchdog expiry must not be reported as a filesystem-integrity failure.

12. **must-fix — C2 does not implement the advertised boundary faults or count its samples.** `src/cases.rs:176`, `:519`, `:553`; `src/host.rs:941`; `src/report.rs:115`.

    Principle: no ACK is a protocol observation, not proof that three publications or a particular sync/fault boundary ran.

    Failure scenario: the guest completes only seq 1, then fails a later write/fsync. It always exits 86 regardless of the error (`host.rs:163`), SSH status is discarded, and one surviving complete frame makes the host set `publishes = 3`. Even the intended path exits only after all three renames; it never faults at each named file-sync/directory-sync/rename boundary. Directory sync errors are explicitly ignored. An unreadable or rejected result slot (for example, a symlink or oversize file) is counted as “not acked”; arbitrary readable bytes count as an ACK without a schema check. All three `not-ack` rows aggregate to `status: ok` and CLI success, concealing incomplete coverage.

    Minimal fix: define and inject the actual three boundary exits, preserve each syscall result/errno, and publish bounded progress/fault-location evidence through the mailbox rather than inferring it from the final slot. Independently observe old/new bytes at each required point and count only observed completed work. An unknown SSH exit/slot read or unproved fault location makes that subcase unknown. Never equate a filesystem protocol error with mere absence of ACK. Aggregate all completed `not-ack` rows as `not-ack` (or explicit `completed-without-ack`), retaining the no-durability claim; reserve `ok` for fully supported successful evidence, not this fallback. See decision #7.

13. **must-fix — C4 reports incomplete or unrelated observations as safety gates and discards the item results.** `src/host.rs:451`, `:491`, `:717`, `:1360`, `:1426`, `:1516`; `src/cases.rs:221`; `src/report.rs:54`.

    Principle: argv requests, file suffixes and one post-operation stat are not observations of actual filesystem/layout/capacity/scratch/first-mount behavior.

    Failure scenario: create uses internal mounts or scratch outside A, or runs when host free space is already below the required 256 MiB. The code does not inspect free space or create scratch/peak/internal-mount/service activity. It nevertheless calls the final image's size/blocks “scratch-bound.” `size-64m` accepts any positive size up to 80 MiB, including 1 byte; `fs-hfsx` accepts any name containing HFS; no-journal is inferred from an image-format description. The boot path permits an unknown journal result and does not require the layout/seeded mounted-tree/ACL evidence. Missing mounted markers are merely a note. The attach item `exec-probe` is always unknown, and setuid/device/cross-UID tests are not implemented. The magic count of twelve accepts duplicate probe IDs, and `report.json` retains only a count and generic `probe-unknown`/`mount-gate`, so a reviewer cannot tell which observations passed or failed. Fixtures also assume a literal `rw` mount-output token; that spelling needs actual Mini verification, not invention from the requested options.

    Minimal fix: record named, typed per-item observations in the report, with unavailable checks explicitly unknown and requested settings distinct from measured facts. Verify the actual HFSX/no-journal/layout/capacity mapping using measured schemas; do not accept generic HFS or “SPARSE” as proof. Add the required host-space preflight and explicit bounded scratch/internal-mount accounting, or block that recipe as unmeasurable. Gate export on all applicable safety observations, including original/mounted directory identities and ACLs. Missing first-mount coverage remains unknown and must not authorize dependent guest runs. Bound the actual option/permission probe list to twelve, rather than padding twelve summary booleans. C10's later service/backup measurements and M7 sandbox/liveness remain unproved; do not promote them from marker presence or `tmutil` success.

14. **should-fix — Replace the raw fstatfs buffer with the correct platform ABI binding.** `src/osutil.rs:121`, `:143`, `:219`; `src/osutil.rs:313`.

    Principle: a byte offset needs a matching ABI and properly aligned allocation; comparing two results on the same filesystem does not verify either.

    Failure scenario: the wrong statfs symbol/layout or an inadequately aligned byte buffer yields stable nonzero bytes that happen to compare equal. The current test still passes, and teardown calls those bytes an FSID. On macOS x86_64, the inode64 symbol distinction is an additional concrete problem; this module currently declares bare `fstatfs` for every macOS architecture.

    Minimal fix: use a macOS-only full `#[repr(C)]` struct and typed `extern "C"` pointer, initialized with `MaybeUninit` and read only after success. For Darwin LP64 the expected layout is: `u32 f_bsize`, `i32 f_iosize`, five `u64` counts, `fsid_t = [i32; 2]` at offset **48**, four `u32` fields (owner/type/flags/subtype), char arrays 16/1024/1024, and eight trailing `u32` words (current spelling: flags_ext plus reserved[7]). Size **2168**, alignment **8**. Arm64 uses `fstatfs`; macOS non-arm64 uses `fstatfs$INODE64` for this layout. Confirm against the Mini SDK header/symbol and add size/alignment/offset assertions plus comparison with independent volume metadata. These details agree with the locally cached libc 0.2.186 Apple definitions; there was no network or Mac SDK verification in this review. A typed complete binding is safer than a prefix struct, packed struct, or oversized byte buffer and adds no dependency. If only the Mini is supported, reject other real targets explicitly.

15. **should-fix — C8 performs no mapping experiment and gives an unsupported reason for the unknown.** `src/host.rs:193`; `src/cases.rs:271`, `:600`, `:625`.

    Principle: listing two account names does not exercise two subjects or show host/guest UID/GID/ACL mapping.

    Failure scenario: two non-admin accounts already exist. Only eval operates, in `.s11-0c/work` **outside the mailbox**, so even its own-file stat/chown attempt measures the guest local filesystem. No host metadata is compared and no second identity is exercised. The report says `second-subject-needs-elevation` without establishing that ordinary access via the second subject is unavailable. It never falsely reports C8 ok, which is appropriate, but the workload does not substantiate its label.

    Minimal fix: preferably delete the unrelated self-ops path and return an explicit `second-subject-not-exercised`/`mapping-not-measured` unknown with the available inventory. If the controller already has approved access to both existing subjects, run the bounded own-object operations on the shared volume and compare both sides' actual uid/gid/ACL/nlink/dev/inode through the result slot. Never create an account, use su/sudo, or broaden credentials to turn this into a pass. Missing capability is an honest partial result.
