1. **should-fix — Tests do not distinguish a fresh guest observation from a constant, cache, or path read.** `gcu-driver-macos/src/scope_os/tests.rs:712`, `:759`.

   **Principle:** A regression test should reject an implementation that violates the property its name claims to test.

   **Concrete failure scenario:** An implementation that returns one plausible constant identity for an existing pid, and `None` for invalid/missing pids, passes these tests. So does a pid-to-executable-path static signature read. A cache of the self identity passes the repeated, cross-instance, and concurrent equality checks because the executable never changes. The forwarding test usefully rejects the old always-`None` blanket behavior, but equality between two calls to the same underlying reader does not independently establish the observed identity.

   **Minimal fix:** Describe these as self-lookup, rejection, forwarding, and concurrency smoke tests; delete the implication that equality proves freshness. For a meaningful macOS regression test, replace redundant self-equality checks with a controlled child executable whose expected identity is independently known, and a case where its pathname is replaced while that child remains alive. Check the original live identity or refusal, never the replacement's identity. This can remain NOT_RUN until a Mac is available; do not claim it was exercised here.

   No shared mutable test state, fixed live pid, or window/AX dependency was found. The absent-pid value is positive, representable, and well above macOS's pid allocation range, so parallel test processes do not normally make it exist. The positive tests assume the test executable has a signature and cdhash (`:709`, `:717`, `:775`); a toolchain producing an unsigned executable, notably an unsigned Intel build, can legitimately return `None` and fail these expectations. That is a signing-environment assumption, not evidence of a lookup bug. CI signing/architecture was not executed or verified.

2. **should-fix — First-array-entry selection is consistent with existing code, but is not a proven canonical live cdhash.** `gcu-driver-macos/src/ffi.rs:284`, `:160`, `:211`; comparison at `gcu-cli/src/helper/scope_link.rs:299`.

   **Principle:** Identity comparisons require an explicit common representation; array position alone does not establish which CodeDirectory hash the parties intend to compare.

   **Concrete failure scenario:** With multiple CodeDirectory hashes, `cdhash_of` chooses `kSecCodeInfoCdHashes[0]` whenever it is nonempty CFData, and only otherwise consults `kSecCodeInfoUnique`. An expected identity using a different array member or the selected unique hash can therefore reject the correct process at admission/ACK/recheck. Lowercasing does not resolve that difference. Selection is deterministic for a given returned dictionary, but the local bindings do not establish an ordering contract across framework results or equate element zero with the kernel-selected hash.

   **Minimal fix:** State the exact first-entry policy and require expected-identity producers to use it. If the contract instead needs the selected/active hash, define that separately and change both producers and observers together; do not silently switch just this call to `Unique`. Prefer one representation over accepting any member of an array.

   This is not a newly demonstrated bypass: `gcu-cli/src/helper/macos.rs:209` has the same first-entry-then-Unique algorithm, and the new guest reader calls the existing driver helper directly. No differing selection algorithm was introduced here. The current `ScopeLease` process model (`gcu-core/src/scope/model.rs:79`) does not itself select or store a cdhash; exact code comparison occurs in the scoped handshake. The real expected-identity production path is not wired by this card, so interoperability with its future hashes remains unproved. A mismatch currently refuses rather than widening admission.

3. **nit — Correct the FFI safety explanations; failure ownership is not a blanket Copy-rule guarantee.** `gcu-driver-macos/src/ffi.rs:300`, `:303`, `:321`, `:324`.

   **Principle:** An unsafe block's justification must describe the API's actual contract, including which result transfers ownership.

   **Concrete failure scenario:** A maintainer reuses these comments with an already populated out-variable and releases it after a failed guest lookup. The documented guest API leaves the out-variable unchanged on failure; its old pointer is not a newly transferred +1 object. In the current code it starts null, so the failure cleanup is a harmless no-op, not an observed double release.

   **Minimal fix:** Delete the unsupported statement that a non-null failure result is necessarily +1, and the unnecessary guest-failure adoption/release. Document success ownership. Do not infer failure ownership for `SecCodeCopySigningInformation` merely from its name: the cached declaration confirms the ABI but does not supply an explicit partial-result ownership contract. Its non-null-on-error cleanup is the one ownership branch I cannot independently confirm from the available local evidence; no concrete bad output from this API was demonstrated.

   Also replace “A null host selects the caller” with “the system code-signing root of trust (currently the kernel).” The cached guest API documentation explicitly says this. Replace “SecCode is a SecStaticCode” with the API's allowance to interrogate a dynamic code reference through a static-code parameter. This is an API-supported implicit conversion, not Rust/C type inheritance. These wording errors do not establish a macOS compilation failure.

4. **nit — Narrow the documentation's observation and race guarantees.** `computer-use/docs/adr/0017-real-eval-fixture-scope.md:174`; `gcu-driver-macos/src/scope_os/facts.rs:119`, `:158`; `gcu-driver-macos/src/ffi.rs:267`.

   **Principle:** Document the guarantees supplied by this code, and distinguish a fresh query from an atomic, validated process-image attestation.

   **Concrete failure scenario:** A reader interprets the ADR's “before and after” start-time claim as a start/code/start transaction around every lookup. `gcu-cli/src/helper/scope_link.rs:234` checks the instance before reading code and returns the code comparison directly; it has no immediate post-read start check. The outer protocol repeats peer checks, including before/after ACK writing (`gcu-cli/src/scope/mod.rs:416`, `:429`), but those are not an atomic bracket around each Security call. A process can exit or exec between observations; a process start timestamp alone is not an exec generation.

   **Minimal fix:** Delete the specific before/after claim and say process-instance binding and subsequent rechecks are caller responsibilities. This documents the existing boundary without reopening the earlier caller implementation.

   Likewise, say “no application-level path-based fallback” rather than promising that Security.framework never consults a backing file. The source does select a live guest by pid and never calls `read_signing`, `SecStaticCode::from_path`, or `executable_path` on this path. However, the cached `CSCommon` header documentation describes dynamic references passed to applicable static-code parameters as an implicit `SecCodeCopyStaticCode` operation. `SecCodeCopySigningInformation` is metadata interrogation; there is no `SecCodeCheckValidity` call here. Backing-file replacement behavior and binding of every returned field to the executing image could not be confirmed from the locally available declarations alone. No replacement-file exploit is asserted by this review, and neither compile success nor the self-equality tests would settle that question. The intended guarantee should be guest-derived signing metadata, not independently validated memory-image identity.
