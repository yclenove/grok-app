## Findings

### 1. P2 — The ready mark can become visible while the guest is still blocked in readiness fsync

**Evidence:** `tools/s11-mailbox-probe/src/c11.rs:274`, `tools/s11-mailbox-probe/src/c11.rs:404`, `tools/s11-mailbox-probe/src/c11.rs:414`, `tools/s11-mailbox-probe/src/c11.rs:453`; write-before-fsync ordering at `tools/s11-mailbox-probe/src/io.rs:594` and `tools/s11-mailbox-probe/src/io.rs:602`.

The host starts round 1 as soon as it reads canonical seq=0. Those bytes can be visible before the guest's readiness `pwrite64` returns: that call still has to finish `fsync`. Consequently, the host can publish seq=1 and start its RTT while the guest remains blocked in the unmeasured readiness operation. Its remaining delay then enters the first RTT and spends the first round's five-second budget. Process-launch delay is excluded now, but the readiness exchange is not wholly outside the samples.

**Reproduction:** ran the unchanged host and guest binaries against local files, interposing only on the guest's first `ip-gh` fsync to delay its return by 1,000 ms. Both roles exited 0 in both modes. Host `rtt_us` was `n=8,min=2911,p50=3740,max=1003868` for fd and `n=8,min=3029,p50=7983,max=1003945` for reopen. Only readiness was delayed; the measured exchanges had no injected delay. The existing readiness test delays publication of seq=0, so it does not exercise this overlap.

**Minimal fix:** gate round 1 on a completion signal emitted after the guest's seq=0 write/fsync returns, under the original command/load deadline. A bounded readiness signal over the existing SSH control channel can provide that ordering without another mailbox pathname; validate it separately from the single guest summary. Add a readiness-fsync-delay test that keeps this delay outside all eight RTTs.

### 2. P2 — C11 preparation still performs export IO outside the bounded runner

**Evidence:** `scripts/s11-0-probe.sh:1005`, `scripts/s11-0-probe.sh:1006`, `scripts/s11-0-probe.sh:1033`, `scripts/s11-0-probe.sh:1037`, `scripts/s11-0-probe.sh:1041`.

The new Python helper correctly creates both files exclusively with no-follow, writes/fsyncs them, and checks their type, size, and link count under `run_bounded`. After that runner has finished, however, `seed_c11_files` calls `c11_seed_visible` synchronously. Its pathname checks and `wc -c` access the export again, with no timeout or deadline postcheck. If that external-volume access stalls, the orchestration shell cannot advance to unknown/quarantine or cleanup. The new stalled-preparation test stalls inside Python and therefore misses this remaining unsupervised path.

**Reproduction:** evaluated the unchanged production functions in a temporary harness using the real bounded runner and Python helper, with a two-second delay only in the post-helper `wc` on `ip-hg` and a one-second remaining probe budget. It returned `seed status=0 elapsed=2s RB_STATUS=0 RB_TIMED_OUT=0 deadline_expired=yes`. An indefinitely stalled check has no supervisor.

**Minimal fix:** remove the redundant shell verification and rely on the checks already inside the bounded helper, or move all verification into that helper. Preserve the existing return-2/unknown/quarantine path whenever completion cannot be proved. Test a stall in verification as well as creation.
