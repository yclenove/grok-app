1. **P1 / must-fix — The list-absence branch still substitutes VM absence for process-exit proof.** `src/disposable/tart/machine/cleanup.rs:376`, `:378`, `:121`, `:186`; fixture at `tests/tart_offline/s11b/recovery.rs:186`.

   **Failure scenario:** Reach `Running` with a provisional pass, revoke successfully, and return a complete successful initial list omitting the clone. `reclaim` immediately returns success without any Tart/Softnet exit evidence. `destroy` sets `vm_cleanup_ok`, and `seal` publishes `Scored(Pass)` with `cleanup_confirmed=true`. The only new evidence was disappearance of the VM name. Guest revoke does not prove that either host process exited. Recovery uses the same branch and can also publish confirmed cleanup without that proof.

   Avoiding name-targeted stop/delete after authoritative absence is correct. The remaining error is treating that absence as sufficient for the separate process-cleanup obligation. Round-1 finding 2 explicitly required establishing that obligation separately. The updated absence fixture starts from `Cloned`, before start, so it does not exercise the dangerous started-VM case.

   **Minimal fix:** Keep the no-stop/no-delete behavior, but fail closed on started/unknown process cleanup unless independent evidence already proves the associated processes exited. With the present fake surface, returning `CleanupFailed` for the unproved case is sufficient; no real process reader is needed. Add a `Running → revoke → initial list absent → seal` negative case that requires no score and no cleanup confirmation, while asserting no name-targeted destructive commands.

2. **P1 / must-fix — A lease can expire inside destroy, after which the abandoned owner still deletes the VM.** `src/disposable/tart/machine/mod.rs:240`; `src/disposable/tart/machine/cleanup.rs:96`, `:388`, `:394`, `:402`.

   **Failure scenario using the supplied fakes:** Reach `Running` at time zero, arm the lease through second 3, and revoke successfully. Advance to second 2. Configure `advance_after_stop(2s)` and provide the normal present/running, stop, stopped/exited, delete, absent replies. Build fresh cleanup deadlines at second 2: query ends at 7, stop/delete at 22. Destroy passes its entry lease check. Stop advances the clock to second 4; the status confirmation still fits its deadline. There is no lease check before delete, so delete is issued by the expired owner and destroy succeeds. A subsequent seal finally enters `Suspended`, too late to enforce the promise that this owner cannot delete.

   This needs neither a timer nor concurrency. The fake clock change occurs between two synchronous inner calls, exactly as the new confirmation-deadline tests already model. No old score survives the later seal check, but the forbidden destruction has already occurred.

   **Minimal fix:** Recheck lease validity before subsequent destructive inner dispatches, particularly delete after stop/confirmation. On expiry, enter the same irreversible hold, leave the row unsealed, and preserve that closed phase through the enclosing error handler. Bound any optional revoke/note by the current call as in finding 3. Add the trace above inside the existing CHECKS child and require no delete, `Suspended`, and recovery required.

3. **P2 / must-fix — Deadline propagation is fixed on the main confirmation path but still bypassed at initialization and in new error/expiry helpers.** `src/disposable/tart/machine/steps.rs:79`, `:97`, `:114`, `:435`; `src/disposable/tart/machine/mod.rs:236`, `:241`; `src/disposable/tart/machine/cleanup.rs:57`, `:67`, `:280`, `:291`, `:537`, `:550`; `src/disposable/tart/machine/recover.rs:151`.

   **Failure scenarios:**

   - Reserve with an attempt absolute deadline at second 1 and a query deadline at second 5. The ledger read, destination list, and reserve call receive second 5: the input absolute is not part of the minimum until after reserve succeeds. The newly added destination query can therefore be permitted to finish outside the attempt it is checking.
   - Shrink `Cleanup` to 2 seconds, reach `Running`, and request the first revoke with its normal 10-second deadline. `admit` computes the effective deadline before `cleanup_origin` exists; the guest receives 10 seconds although the cleanup end is 2. The new test `cleanup_end_clips_the_stop_deadline` performs this exact first revoke at `tests/tart_offline/s11b/review.rs:559`, but inspects only the later stop deadline.
   - Arm through second 3, retain a revoke-call deadline ending at second 1, advance to second 3, then call revoke. `ensure_phase` detects expiry before `admit` and invokes `expire_owner(None)`. That helper dispatches guest revoke with a fresh deadline at second 13 and a ledger note at second 8 despite the triggering call already being expired. Late renewal takes the same `None` path. Even the `Some(requested)` path omits the attempt absolute and aggregate bounds. Entering the hold must remain unconditional; these optional IO calls must not gain new time.
   - Finish cleanup and call seal with a 1-second deadline, injecting `ReplyLost` or `CommittedLost`. The new readback uses `query_deadline_from_now`, allowing 5 seconds, regardless of the seal's effective end, attempt absolute, or cleanup end. Recovery failures also call this helper from `stop_recovery`, extending a short caller query deadline. These passed instants are wrong even with immediate fake replies; no sleeping adapter is needed to expose the defect.

   **Minimal fix:** Pass the relevant caller/effective end into every helper that dispatches IO. Include the reserve input absolute and the first cleanup end before dispatch. Make the expiry state decision independent of IO, skipping optional calls when no bounded time remains. Delete `query_deadline_from_now`; use the remaining enclosing minimum for readback, or conservatively report recovery required when readback cannot fit. Keep recovery independent of the dead row's absolute deadline. Assert ledger and guest deadlines as well as runner deadlines, including expired-entry and first-revoke cases.
