**Must-fix**

1. **[P1, R2-1] Invalidation between admission and watcher setup can still deliver after revoke.**

   Changed code: `gcu-core/src/scope/driver.rs:292`, `:294`, `:295`, `:298`; `gcu-core/src/scope/model.rs:488`, `:519`, `:536`. The router independently uses the same subscribe/mark-seen pattern at `gcu-core/src/action/router.rs:446`.

   `perform` copies generation 1 and runs `guard::rewrite` **before** subscribing. Revoke/rebind may happen during that interval, including while a metadata evidence query is in progress. A newly created watch receiver considers the existing value seen; `borrow_and_update` also discards any update between subscription and that call. There is no subsequent comparison of the opened scope before polling `inner.perform`. Additionally, `Sender::send` does not retain an update when there are no receivers; the code explicitly ignores that error.

   Concrete direct-API trace: copy generation 1; hold an evidence lookup in `rewrite`; revoke; finish the lookup with the previously admitted binding; subscribe/mark seen; poll an inner fake that checks an initially uncancelled `Cancel` and delivers. No future watch update is needed or guaranteed. `finish_perform` eventually reports unknown, but cancellation and release did not precede delivery even though revocation did. This gap exists before entering the native adapter and is independently testable in S1.

   Required fix: arm invalidation before taking the operation's authority, then compare that same authority after watcher setup and before starting work; do not mark a possibly intervening update seen without validating it. Keep the authoritative state and notification protocol consistent, including the zero-receiver case. The native delivery-point permit remains separate S2/S4 work.

   Regression needed: a barrier in admission/evidence before watch registration, and a barrier between registration and mark-seen; revoke and rebind separately. Assert refusal, zero delivery, cancellation, and release counters. `fixture_scope_round2.rs:100` pauses **inside** the inner perform, after watcher setup, so it cannot catch this gap.

2. **[P1, R2-2] The subscription wrapper neither wakes pending consumers on invalidation nor revalidates the subscribed window.**

   Changed code: `gcu-core/src/scope/driver.rs:310`, `:367`, `:378`.

   `ScopedEvents` stores no watch receiver, invalidation future, Stop notification, or registered invalidation waker. It checks booleans only when somebody polls it. If `next()` has already returned Pending on a quiet inner stream, revoke/rebind or Stop alone does not wake that task. The pending operation and native subscription can remain alive indefinitely. Returning `None` on a later externally triggered poll does not establish termination on invalidation.

   There is also a surviving information channel: the wrapper retains only run/generation, not the admitted `WindowBinding` or live evidence. Keep the lease generation unchanged, replace/reuse the window incarnation or owner, then have the inner stream emit `Changed`, `GeometryChanged`, or `WindowGone`. The event passes both checks. The old subscription still reports activity for a window no longer admitted by its exact binding.

   Required fix: make invalidation and Stop wake and retire a pending stream, release its inner subscription, and validate exact window ownership/incarnation before forwarding events. A trusted binding invalidation mechanism is acceptable; checking only the lease epoch is insufficient.

   Regression needed: start and poll a quiet `next()` to Pending, then revoke/rebind/Stop **without pushing an event**; assert completion and native unsubscribe/drop. Separately change owner/incarnation without rebind, emit an event, and assert no event reaches the caller. `fixture_scope_round2.rs:178` pushes an event before awaiting again; its Stop case (`:187`) also starts the assertion after Stop. Both stay green with the missing wakeup. Neither changes identity.

3. **[P1, R2-3] A generation-1 approval can still be consumed by a generation-2 action after recheck.**

   Changed binding/recheck code: `gcu-core/src/action/authorize.rs:237`, `:297`, `:341`; dispatch context: `gcu-core/src/action/router.rs:363`, `:373`, `:376`; changed driver opening: `gcu-core/src/scope/driver.rs:292`.

   The new checks compare approval epochs during `authorize` and `recheck`, but no expected approval epoch crosses the final dispatch boundary. The driver opens whichever generation is current when perform begins. Its watch protects that newly opened generation, not the generation that authorized the action.

   Concrete trace: approve and finish rechecking a PressKeys request in generation 1; rebind to generation 2 retaining A and its window before perform opens its scope. The intervening `driver.subscribe` is a convenient deterministic barrier for a fake. Dispatch then starts with a new cancellation token and new watchers at generation 2. The action contains no sealed handle, so rewrite admits it and delivers. Generation-1 grants/confirmation have authorized a generation-2 action without a new decision. This does not depend on a missed watch update in R2-1: every generation-2 operation can observe a perfectly current lease.

   Observation has the analogous boundary: `observe_enqueued` checks the approval at `router.rs:162`, then awaits resolve and another full read (`:172`, `:186`) and publishes without checking the approved epoch again. `expect`/`wait_for` discard the returned `Approved` altogether (`gcu-core/src/action/expect.rs:74`; `action/wait.rs:97`). A retained target can therefore be observed under a new generation using the prior generation's authorization.

   Required fix: carry one expected epoch from authorization through dispatch and observation completion, reject a different epoch at the operation boundary, and cancel the whole authorized attempt when that epoch changes. Reading the current epoch independently at each stage does not bind those stages together.

   Regression needed: rebind after successful recheck but before perform opens, with the same app, window, geometry, tree, and policy. Use PressKeys and assert a new decision is required or the call refuses with zero delivery. Also rebind after observation authorization before its second read. The new confirmation tests rebind inside the approval callback (`fixture_scope_round2.rs:631`), which exercises an earlier check only.

4. **[P1, R2-4] A scope invalidation reported as unknown still returns a batch's old state.**

   Changed code: `gcu-core/src/batch/executor.rs:59`, `:111`; `gcu-mcp/src/result.rs:145`; invalidation classification: `gcu-core/src/scope/driver.rs:345`.

   Concrete trace: step 0 succeeds for A and retains an `ActionState`; step 1 starts delivery; revoke the lease; step 1 finishes with possible execution. The wrapper correctly returns `Native { maybe_executed: true }`, so the router reports `Outcome::Unknown` with `ErrorCode::DriverError`. Batch hard-stops on unknown, but `scope_hard_stop` matches only fixed-message `AppDenied`. It keeps step 0's state. MCP applies the same narrow predicate and emits that state, including any retained image/overflow file, after A's authority is gone.

   This is the remaining part of R1-4, made explicit by the newly introduced invalidation-to-unknown path. Changing unknown to refused would misrepresent delivery and is not the fix.

   Required fix: bind retained batch output to the attempt epoch and validate it at return/encoding, clearing stale state independently of the particular error code. Preserve the truthful unknown action result and historical unscoped behavior.

   Regression needed: `final_state=true`, `stop_on_error=false`, a successful first step with retained output, and revoke/rebind during an already-started second step. Assert unknown, no third-step delivery, and no retained top-level/error state, attachment, or newly exported stale file. The new batch regressions (`gcu-core/tests/fixture_scope_round2.rs:313`; `gcu-mcp/tests/fixture_scope.rs:863`) only produce the fixed `AppDenied` path.

5. **[P1, R2-5] New observation tags can relabel an old wait sample as belonging to the current generation and publish it after revocation.**

   Changed code: `gcu-core/src/action/wait.rs:205`, `:206`; `gcu-core/src/action/observe.rs:190`, `:310`; `gcu-core/src/snapshot/store.rs:259`. Supporting call path: `gcu-core/src/wait/mod.rs:220`, `:315`; `gcu-core/src/action/wait.rs:148`, `:208`.

   The tags are sampled at assembly/publication time, not carried from the operation that produced the payload. `publish_with_limit` records the state and copies those tags without validating them against the lease or the producing operation.

   Concrete trace: `wait_for` takes a valid generation-1 A sample, fails to match, and retains it. Revoke (or rebind to generation 2 containing only B) between that sample and a deadline occurring before the next 150ms poll. The wait engine checks session/Stop/turn, not the scope, and returns its held A sample on timeout. `observation` stamps it with `None` after revoke, or generation 2 after rebind, then publishes A's text/window state alongside Timeout. Closing the scoped event stream does not fix this: an ordinary stream EOF switches the engine to polling rather than producing a scope denial (`gcu-core/src/settle/events.rs:78`).

   Thus the per-driver post-await checks can all pass and the caller can still receive a payload after its generation lost authority. The new snapshot metadata can even certify the wrong producing generation. This is an in-memory core result lifetime, independent of S4's deferred persistent image/file-cache retirement.

   Required fix: capture the attempt/sample epoch before reads, retain it with every held sample, and validate it before publication, including timeout and error-state branches. Reject rather than replacing a stale/missing stamp with the current generation. Ordinary `read_with_mode` should likewise preserve one producing epoch across its multiple awaits.

   Regression needed: a controlled wait clock/barrier after a real held sample and before timeout; revoke and remove-A rebind separately; assert the fixed denial with no text/state/image and no new snapshot. The new held-driver-call tests do not pause a sample already returned by the wrapper.

**Additional nice-to-haves and verification limits**

- The held-call barriers are real cooperative barriers: `fixture_scope_support/mod.rs:303` marks entry and waits for a separate release, without holding the evidence mutex across an await. However, the “already started” fake (`:596`) reads a boolean before pausing, then increments the delivery counter and returns success **after** release (`:605`), bypassing cancellation. It verifies conversion of a late successful result to unknown; it does not demonstrate an input-down effect before invalidation or its cleanup. Model an actual started effect/held-input ledger before the barrier, and assert both pre-revoke and post-release counters. Give barrier waits a bounded timeout so a broken entry path fails instead of hanging.
- Add direct epoch-matching grant tests and assert approval counts after rebind. The second observation in `fixture_scope_round2.rs:300` only asserts success; it would still succeed if an old grant were incorrectly reused. Existing `policy/grants.rs` changes add `None` fields but do not test the new `ScopeEpoch` difference or `covers_in` mismatch cases.
- Cover Stop on inner-error returns as well as successful-inner returns. In the wait-engine sampling path, let the inner snapshot latch Stop and revoke, then return a nonexecuted error. `scope/driver.rs:225` returns through `map_err(...)?` before the new Stop-aware handoff, and `wait/mod.rs:346` returns its error code without another boundary check. The tool can report scope/driver error instead of `stopped_by_user`. This is a surviving call-path limitation, not a new input bypass; the new perform-only Stop test does not cover it.
- Check the epoch of the screenshot actually selected, not only the latest snapshot. `authorize.rs:330` checks `latest`, while `action/gate.rs:85` and `router.rs:556` use `latest_with_screenshot`, which may select an older generation after a newer screenshot-free observation. Add a canvas/no-hit-node case so sealed-handle differences cannot mask use of an old screenshot. Snapshot/cache retirement work should make the intended boundary explicit.
- Retire obsolete epoch grants rather than accumulating one entry per generation for the same app (`policy/approval.rs:152`). The new `SnapshotStore::set_scope_epoch` also adds the full run length on every call, including retagging (`snapshot/store.rs:273`); it should account for replacement and define whether retagging is legal. These are retention/accounting concerns; I did not establish an independent model-controlled memory-exhaustion bypass.
